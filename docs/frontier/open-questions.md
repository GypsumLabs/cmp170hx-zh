# 未解问题登记表

**本页覆盖内容。** CMP 170HX 上的每一个未解决问题，均汇总自全部 24 份已裁决的领域文档，经过去重，并按可处理性而非重要性排名。每个条目都会说明：想要确认什么、已经尝试过什么、为何失败、什么证据可以定论，以及最有希望的下一步。

最值得知道的一点是，**开放清单中有很大一部分问题成本很低**。Tier 0 中有六个条目完全不需要硬件，只需查看一个头文件、计算一个哈希，或执行一次 `--dry-run`。Tier 1 中另有十几个问题只需要一张卡、一次重启和一条事后贴出的日志。真正困难的问题（NVLink、ECC、Gen3）之所以困难，是因为存在明确的原因；下文会把这些原因写出来，而不是含糊带过。80 GB 曾经属于这一类，如今已经不再是：折叠现象已有解释并消失，剩下的问题范围更窄（见条目 1.1）。

归档期间关闭的条目会保留在原位置，标记为已关闭并记录结果，而不是删除。除非明确注明，否则下方没有任何条目仍处于开放状态。

如果想查看当前的能力状态，而不是未解问题，请参阅[状态板](status-board.md)。

## 条目如何排名

| Tier | 关闭成本 |
|---|---|
| **Tier 0** | 无需硬件。一个文件、一个头文件、一个哈希、一次离线 dry-run，或一次代码改动。 |
| **Tier 1** | 一张卡、一次引导或一条命令。事后贴出一条日志即可定论。 |
| **Tier 2** | 一张卡加一次重建、一次受控 A/B 测试，或一次插桩运行。 |
| **Tier 3** | 新能力：需要设备、现有人员没有的硬件，或尚未有人实现的技术。 |
| **Tier 4** | 测量争议。与其说是未知，不如说从未在统一的方法论下测量过。 |
| **不可回答** | 记录或代码中没有任何东西可以定论。 |

## Tier 0：无需接触显卡即可定论

### 0.1 LMR 幅值字段宽度

**想要确认：** GA100 上 `NV_PFB_PRI_MMU_LOCAL_MEMORY_RANGE` 中 `LOWER_MAG` 的宽度：是 `[9:4]` 的 6 位，还是 `[10:4]` 的 7 位。
**已经尝试：** 只做过算术推导。在 6 位字段的假设下，规则 `size_MiB = MAG[9:4] << SCALE[3:0]` 对实际使用的全部五个值（`0x208`、`0x288`、`0x20B`、`0x28A`、`0x28B`）都能精确匹配，而 `0x50A` 会解码为 16384 MiB，而不是 81920 MiB。在 7 位字段的假设下，`0x50A` 则会变成 `80 << 10` = 81920 MiB。
**为何仍是开放问题：** 还没有人读取 `dev_fb.h`。
**可以定论的证据：** 头文件中的定义。这是一次查找，不是一次实验。
**为何重要：** 这是解决 `0x28B` 与 `0x50A` 之争、得到明确答案的最后一道障碍，而这场争论又直接关系到 80 GB 重试（条目 1.1）。

### 0.2 移植分支中的七个未验证小版本是否适用？

**想要确认：** 要么通过模糊匹配确认适用，要么将 `clanker/driver-port` 分支 `driver/VERSION` 中列出的七个驱动版本从白名单中移除，因为没有任何 `constants.yaml` 条目为它们提供支持。
**已经尝试：** 什么都没做。这个风险是通过阅读代码发现的。
**下一步：** 下载每个 tarball，并针对匹配的主版本补丁目录运行 `patch -p1 --dry-run`。整个过程纯离线且机械化。

### 0.3 `booter_load` 在驱动 535 到 610 之间真的没有变化吗？

**想要确认：** 一个实际操作依赖的说法（“extract once”）是否成立，即把以 580 命名的二进制交给 610 时代的链路使用。
**已经尝试：** 这个说法被断言过两次，但从未展示证据。任何地方都没有跨版本哈希。
**可以定论的证据：** 对 `g_bindata_kgspGetBinArchiveBooterLoadUcode_GA100.c` 中 535.x、580.x 和 610.x 的 `IMAGE_PROD` 条目解压后内容计算 SHA-256。
一个相关且同样便宜的做法，是对同一 bindata 档案中的 `IMAGE_DBG` 和 `IMAGE_PROD` 计算哈希，从而确定由调试版本派生的 ROP 链是否保证能在生产晶片上工作。

### 0.4 修正 `0008` 的重训练成功判断条件

**想要确认：** 让驱动日志如实反映 Gen2 状态。`LnkSta 0x1042` 是一条真实的 Gen2 链路，但 `0008` 的成功判断把 `PCI_EXP_LNKSTA_DLLLA`（位 13）包含在内，而这一位永远无法被设置，因为 GPU 的 `LnkCap` 位 20（DLL Link Active Reporting Capable）为 0。
**后果：** 补丁会在一条正常工作的链路上打印失败；这已经误导一份下游分析得出 `0008` “runs too late”（运行得太晚）的结论。
**下一步：** 删除 DLLLA 条件，或让它以 `PCI_EXP_LNKCAP_DLLLARC` 为条件，或改为从上游桥而不是端点读取 `LnkSta`。这只需修改 `0008-pcie-gen2-probe-retrain.patch` 中的一行。

### 0.5 工具报告缺口

以下是三个无需硬件即可完成的自包含补充：

- 将已发布解锁器实际操纵的五个 PLM 地址加入 `probe.sh`：FBPA PLM `0x009a0148`、WPR PLM `0x001fa7c4`、WPR_CFG PLM `0x001fa7cc`、WPR2 lo/hi `0x001fa824` / `0x001fa828`，以及 MMU LMR `0x00100ce0`。现有的 120 个寄存器目录早于解锁器建立，完全没有覆盖这五个地址。
- 给 `verify.sh` 增加 PCIe 检查。它目前在任何分支上都不检查链路速度，**包括 Gen2 谱系**，因此那个 README 声称 Gen2 “Working”的分支，发布的验证器却根本看不见 Gen2。
- 固定或校验 `open-gpu-kernel-modules` tarball。`build.sh` 使用 `curl -L --fail` 获取并缓存它，但整个代码树中没有任何校验。

### 0.6 Gen2 和多卡支持的合并阻塞者

**想要确认：** 让默认安装包含 Gen2 和多卡支持。
**代码树中可见的阻塞者：** `0007` 是一大段带调试插桩的代码，始终以 `LEVEL_ERROR` 记录日志；`tools/retrain.sh` 在当前 Gen2 谱系中是死代码（`Gen2`、`far` 和 `deced` 都会在安装时 `rm -f` 它，只有更早的 `debug-gen2` 分支曾安装过它，而且它的硬编码 BDF 只在 `deced` 上被修正）；`constants.yaml` 遗漏了该机制依赖的五个寄存器。
**下一步：** `multiple-cards` 的安装器改动（`b1cb6d8`）是自包含的，可以单独合入，不依赖 Gen2 PCIe 补丁。Master 的补丁 `0001` 已经内置两种几何布局，因此 `mixed` 配置无需改动驱动即可工作。

## Tier 1：一张卡、一次引导

### 1.1 折叠消失后，什么仍在限制 80 GB？

**在免驱动路径上基本已经回答；驱动内构建仍未用这一结果重建。**
**原先的开放问题：** `80` 分支恰好在 40 GiB 处发生的折叠，究竟来自不连贯的 LMR，还是来自 LTC 解码。按编译结果，该分支将 CFG1 `0x02779000`（`0x77` 档位，每个 FBPA 4096 MiB，20 个 FBPA 共 81920 MiB）与 LMR `0x0000028A`（40960 MiB）以及 `fb_length 0x1400000000`（80 GiB）一起编程。三层给出了三个不同的答案，而折叠边界与 LMR 完全吻合。

**2026-07-25 已在免驱动路径上回答。** 一次 fire 操作同时使用 LMR `0x028b`、CFG1 `0x02779000` 和 `0x10000300` 处的 L2 解码，启动后得到**总计 79.3 GiB、空闲 79.0 GiB**，并获得一个**不会折叠的 77 GiB** 缓冲区：偏移扫描越过原先 40 GiB 的碰撞点后仍然读到了真实带宽。这次运行后来在频道内被总结为 “80GB seems to be verified in tests”（80 GB 似乎已经在测试中得到验证）。2026-07-27 又在出厂引导时序下完成了一次 72 GiB、无折叠的运行。因此，连贯 LMR 假设得到了支持，LTC 解码并不是不可逾越的障碍。

**仍然开放的问题**已经比该条目原来的范围窄得多：

- 40 GiB 以上的带宽约为峰值的 79%，而不是低偏移处看到的约 98%。
- 每次 fire 操作在 Xid 154 之前只有大约一个 CUDA 上下文能够存活。
- 还没有人用编译后的驱动复现其中任何一项。在 `driver/patches/0001-sec2-postbl-plm-ss-cfg.patch` 中设置 `lmrValue = 0x0000028BU`，**并且**在 `driver/build.sh` 中设置 `LMR="0x0000028B"`（不能只改 `constants.yaml`，因为构建过程根本不读取它），这些改动至今仍未编译，也未引导验证。

参见[80 GB 问题](80gb.md)。

### 1.2 `RMPcieLinkSpeed=0x1` 还是 `0x2`？

**想要确认：** Gen2 的正确 modprobe 行。
**状态：** 两种写法都已发布。`debug-gen2/install.sh:191` 和 `Gen2/install.sh:280` 写入 `NVreg_RegistryDwords="RmForceEnableGen2=1;RMPcieLinkSpeed=0x1"`；`far/install.sh:280` 和 `deced/install.sh:280` 写入 `0x2`，后者由提交 `8854d3e` “Remove clamp link to Gen1” 引入。两种解释在内部都说得通，取决于该键的含义是 “clamp to gen N”（钳制到第 N 代）还是 “enable up to gen N”（启用到最高第 N 代）；而 README 声称 Gen2 可用的那个分支，发布的是 `0x1`。
**下一步：** 在同一张卡、同一个内核上分别引导三次（不设置该键、设置 `0x1`、设置 `0x2`），每次都贴出 `LnkSta`。成本低，而且能直接定论。

### 1.3 595 / 590 / 580 驱动移植版能引导吗？

**已经尝试：** 该分支于 2026-07-21 发布，并明确呼吁测试者进行验证；之后没有反馈。
**为何停滞：** 这需要一位愿意将正常工作的卡降级的持有者。
**可以定论的证据：** 每个分支找一位测试者，报告 `dmesg | grep SEC2_DEBUG` 和 `POST-BooterLoad verify` 行。这一行就能回答问题。

### 1.4 `610.43.02` 还是 `610.43.03` 更可靠？

这个问题曾在频道内被直接提出，但从未得到回答。两个版本都有成功解锁的记录；`610.43.03` 只是 `driver/VERSION` 中排在前面的版本。
**下一步：** 从现有安装基础中收集 `driver_version` 元数据文件以及 SEC2 PLM 打开成功率，然后比较两者。

### 1.5 MIG 在解锁卡上可用吗？

与 MIG 相关的寄存器都已填充且可读（`FBHUB_MEM_PART_BOT 0x00100b88`、`MID 0x00100b8c`、`BOUNDARY_CFG0 0x00100b90`、`SYSMEM_HSHUB_CONNECTION_CFG 0x00100b98`），而熔丝调查显示，170HX 是**没有编程 MIG 分区**，而不是 MIG 已被熔丝关闭。另有独立实验演示了通过 `0x820840` 的位 0 启用 MIG，并报告该设置可以持久保留。
**已有一次报告：** 在一张解锁卡上，`nvidia-smi mig -lgip` 恰好列出一个配置档位 `MIG 1g.64gb`（63.00 GiB、70 个 SM），`nvidia-smi mig -cgi 0` 可以创建它；而标准 A100 配置档位（`-cgi 9,3g.20gb -C`）返回 `Invalid Argument`。因此，MIG 可以打开，但无法像已发布的分区卡那样对该卡进行分区。
**下一步：** 在第二张卡上重复实验，并找出 RM 构建 GA100 GPU 实例配置档位列表的位置，以便加入更多档位。如果启用结果能够保持，便提交拉取请求；维护者已经表示愿意合并一个。

### 1.6 P2P 在纯 170HX 主机上有实际作用吗？

**已经尝试：** 树外 P2P 补丁已经构建进一个 cmpunlocker 代码树。一位测试者报告它在纯 170HX 主机上没有效果。当天另一份阳性报告来自一台还装有两张 RTX 3090 的机器，而负面报告称唯一能工作的正是这种混合型号场景。
**可以定论的证据：** 一台纯 170HX 多卡主机的 `p2pBandwidthLatencyTest` 连通性矩阵，分别测试带补丁和不带分层补丁的情况。这个测试成本低，结果也不会含糊。
**注意：** 所有相关人员都同意，P2P 受带宽限制，在 Gen1 x4 上实际收益很小。

### 1.7 Gen2 x16 的长期稳定性

复现问题已经定论：两台机器、五张卡、两个板卡修订版，配合 `lspci` 捕获，在连续四卡负载 90 分钟内没有出现 AER 错误。参见[现场报告](../operations/physical-mods.md#field-report-four-cards-at-gen2-x16)。

目前缺少的是持续时间。还没有人公布持续负载数天后的错误计数器，而这正是边缘状态的交流耦合网络最后可能暴露问题的方式。
**下一步：** 任何让电容改装卡以 Gen2 x16 运行的人，都应在连续运行一周后贴出 `cat /sys/bus/pci/devices/<bdf>/aer_dev_correctable`，同时附上 `lspci -d 10de:20c2 -vv | grep -E 'LnkCap:|LnkSta:'`。

### 1.8 `0x008200FC` 读出的是什么？它可以写入吗？

目前有三种互不相容的观察结果：2026-07-09 读到 `0x000003FF`，写入失败，直接从主机执行 `writel` 也被限制在 `0x3FF`；2026-07-16 在整个 Ampere 产品线都读到 `0xffffffff`；以及 2026-07-23/24 九个 PLM 分支工具报告 `PLM[8] OPT_PLM(0x8200fc) attempt=0 status=0xffff reg=0xffffffff`，并将其标记为成功。同一个寄存器有两个名称：分支代码中称为 `OPT_PLM`，净室工具中称为 `FUSE_SS_PLM`。
**下一步：** 在一张冷引导、尚未进行任何解锁的卡上读取 `0x008200FC`，然后在九次 PLM 打开操作中的每一次之后，都对同一块卡再次读取。

### 1.9 RAMCFG 重新跳线的结果（已关闭）

> [!TIP]
> **2026-07-25 已关闭：确认结果为阴性，符合预测**
>
> 一张 10 GB 卡上的 RAMCFG 电阻被移到了 `HHLLH`，也就是 8 GB 出厂跳线模式。卡能够引导，而 `probe.sh` 从 `0x009a0204` 处的 `FBPA_CFG1_BROADCAST` 读到的仍然是 **`0x02449000`**，即 10 GB 的数值。频道内将结果总结为 “the resistor change had no effect”（电阻改动没有效果）。这正是**从代码预测的结果**：驱动根据 PCI device ID 选择几何布局，而不是根据跳线选择。值得注意的是，该卡在 L2 解码已经处于 `0x10000300` 的情况下成功引导。通过物理方式重新设置 RAMCFG 跳线无法改变容量，是一条失败路线。

### 1.10 驱逐测试中的折叠会在发布版几何布局上复现吗？

显示 8 GiB 边界以上均匀的峰值 79% 平台的偏移扫描，过去只在被放弃的 80 GB 配置上运行过。当前发布版 master 会对两个 device ID 都将 BAR0/PRAMIN 限制在恰好 8 GiB，这一点很有提示性，但 PRAMIN 是 CPU 孔径，而该扫描执行的是设备侧 memset。
**下一步：** 在一张发布版的 8 GB 至 64 GB 卡上，重复完全相同的偏移扫描和块扫描。如果台阶在 8 GiB 处再次出现，说明它是几何布局效应；如果没有出现，则说明它是过度 fire 特有的现象。

### 1.11 uBatch 悬崖

一张拥有 84 个 SM、其中 68 个可用的 CMP 100-210 显示，将一个 `n_ubatch` 标志调到略低于 SM 数的位置，可带来 **3.04 倍提示处理增益**。还没有人在 70-SM 的 170HX 上运行过等价实验。
**下一步：** 在算力解锁卡上使用 `llama-bench`，将 `n_ubatch` 从 48 扫描到 80。这是资料库中成本最低的未测试性能线索。

### 1.12 记录节流开始的温度

目前同时存在四个温度数字：观察到 80 C 时发生节流、社区报告的 85 C、驱动报告的 `GPU Max Operating Temp 85 C` / `GPU Slowdown Temp 95 C`，以及一份散热失效时超过 100 C 才发生节流的描述。这些数字可能分别对应不同层级，因此都可能为真，但还没有人捕获过一次节流日志。
**下一步：** 使用 `nvidia-smi --query-gpu=temperature.gpu,clocks.sm,clocks_throttle_reasons.active`，记录温度从 75 C 上升到 95 C 的全过程。

## Tier 2：一张卡加一次重建或受控 A/B 测试

### 2.1 10 GB 卡上的中间容量

**想要确认：** 得到介于稳定的 40 GB 和会出问题的 80 GB 之间的容量。这个问题曾在频道内被直接提出，得到的回答是 “I don't believe its been tried.”（我认为还没有尝试过）。
**为何明显路线不可行：** 每通道档位过于粗糙（`0x44` / `0x66` / `0x77` = 512 / 2048 / 4096 MiB），因此仅靠档位无法得到中间容量。
**下一步：** 将 CFG1 固定为 `0x77` 档位，再通过 `targetFbBytes` 将驱动可见容量限制为 48、56 或 64 GB，然后在每个梯级运行先写满再读满的折叠测试。每个梯级只需改一个常量并重启一次。这也是反驳“坏堆叠分档”理论的决定性实验。

### 2.2 广播写入还是逐个 FBPA 写入 CFG1？

当前发布版驱动只将 CFG1 写入广播别名 `0x009a0204`。唯一一次报告没有出现幻影回读的实验，是逐个写入所有 FBPA。还没有人插桩确认 FBPA 广播是否是真实的 PRI 特权环硬件机制。
**下一步：** 打开 FB 几何布局相关的 PLM、禁用 devinit，只写广播地址，然后读取 24 个逐 FBPA 的 CFG1 镜像（`0x00900204 + n*0x4000`）以及 `CSTATUS_RAMAMOUNT`（`0x0090020C + n*0x4000`）；随后改为逐个 FBPA 写入并比较两组结果。

### 2.3 究竟哪个 PLM 控制 LMR？

**想要确认：** 找到保护 `0x00100CE0` 的权限掩码，使 LMR 可以从主机写入，而不必执行 HS fire。有人贴出过一张候选 FBHUB 表，随后又被其作者本人否认。
**没人采取的捷径：** 当前发布版驱动在恰好打开四个 PLM 后，**确实**能够从主机成功写入 LMR，因此这四个 PLM 中已经有一个在控制它。对发布版 `plmTable[]` 做一次四路消融实验，就能找出是哪一个。

### 2.4 CFG1 首位数字是什么意思（已关闭）

> [!TIP]
> **2026-07-27 已关闭：位 29 会将档位减半**
>
> 实验已经完成。在一张有 20 个可用 FBPA 的卡上，将 CFG1 `0x22779000` 写入原本为 `0x02669000` 的位置，**使 `0x77` 档位减半**为每个 FBPA 2048 MiB，得到 20 x 2048 = 40960 MiB（40 GB）。在这次改动前后，每个 FBPA 的 `CSTATUS` 都保持为 `0x0800`，LMR 都保持为 `0x0000028a`，因此容量变化来自 CFG1 本身。
>
> 时序块还出现了第二个效果：`0x9a038c` 处的 `HBM_CFG0` 从 `0xa7` 变为 `0xa6`，也就是双 rank 位发生变化；7 个时序寄存器中有 6 个切换到了跳线 5 的值。因此，首位数字不是单纯的容量除数；它会重新选择 rank 配置，并连带改变时序跳线。候选 VBIOS 跳线条目 `00 90 77 22` 携带同样的奇数 `2`，与这一解释一致。
>
> 这次写入可能需要 ROP 路径；这一点据报告还不能完全确定。

### 2.5 通过尝试 Gen2 熔丝的同一张表来尝试 Gen3

**值得进行一次引导尝试，但先验概率很低。** 23 项 `xp3gTable` 确实包含 `FUSE_PCIE_GEN23_DIS 0x0082057c`，但在晶片上观察到这次写入*失败*（`status=0xffff rd=0x00000001`，随后出现 `SEC2_DEBUG: PCIe xp3g booter FAILED to set OPT_GEN23`），因此没有证据证明该熔丝组存在可以扩展到 `0x00820580` 的写入路径。Gen2 是通过 `CYA_0` / `LINK_CONFIG_0` / XP3G / `PRIV_MISC_1` 覆盖，再加上根端口重训练实现的，而不是通过那次熔丝写入实现的。`FUSE_PCIE_GEN3_DIS 0x00820580` 读为 `0x00000001`，**从来没有人写过**，而且没有任何代码路径请求过高于 2 的目标链路速度。
**下一步：** 在同一张表中加入 `0x00820580 = 0`，然后请求 TLS = 3 并读取 `LnkCap2`。如果它变为 `0x0000000E`，则连续性论证成立；如果保持为 `0x00000006`，则说明 Gen3 熔丝在下游被独立强制执行，而目前证据更支持这种解释（将 PHY 速率强制为具备 Gen3 能力的 `0x00340036` 后，链路仍停留在 Gen1）。

### 2.6 第二组特性覆盖寄存器

从 PL0 读取时，`0x823830` 到 `0x82383C` 返回 `0xbadf5040`，而从 HS 读取时会返回真实值。这一组没有手动 PLM 覆盖，也从未执行过 HS 写入后回读。相关且同样未测试的项目是：将 `0x823b00` 作为 `0x823824` 处行重映射器的候选 PLM。

### 2.7 隔离 SS1

“SS1 nerfs 64-bit compute”（SS1 削弱 64 位算力）这一说法，是一个恰好紧邻正确 FP64 测量结果的未验证信念。SS1 自 2026-07-14 起就已加入配方，并且始终与 SS0 一起发布。
**下一步：** 做一次删除 `0x00823820` 写入的一行构建，然后重新运行 OpenCL FP64 测试。如果这个信念是错的，预期结果为 6.421 TFLOP/s；如果它是对的，结果应接近 0.19。

### 2.8 为什么 INT8/IMMA 仍然受门控？

一张解锁卡的 INT8 速度为 44.1 TOPS，大约比自身的 FP16 **慢 3.7 倍**；而 A100 的 INT8 约为 FP16 的 2 倍。IMLA 熔丝读数与 FMA 熔丝相同，都是 `0x5`，SS0 对它们设置的覆盖半字节也相同，但实测速率并没有相应提升。另一方面，原始 MMA 路径测得 335 TOPS，而库路径（torch、cuBLAS、OpenCL）只有 43-48 TOPS。
**下一步：** 使用 INT8 输入，执行一个明确指定 `CUBLAS_COMPUTE_32I` 的 GEMM，并与原始 MMA 数字对照；同时转储 `0x00823818`，配合按数据类型区分的微基准测试，检查*有效的* IMLA 字段是否真的为零。

### 2.9 残余算力门

- `SM_ISSUE_RATE_MODIFIER 0x00504204` 在一张完全解锁的卡上读为 `0x00000005`，解锁过程不会触碰它。虽然该寄存器在 PL3 下可由主机写入，且写入原语已经存在，但还没有人将其写为 0 后重新运行基准测试套件。
- `SKED_UNK54 0x00407054` 是 GSP 固件中被引用次数最多的未文档化 SKED 寄存器（13 处引用），也是 13 张卡的样本中唯一在 170HX 上非零、而在 A100 和 RTX 3090 上都为零的寄存器。还没有人进行写入测试。驱动在 GR init 期间会清除它，因此只能在驱动加载前观察到。
- `FEATURE_READOUT_1 0x00823818` 没有已知的字段布局。对出厂值 `0x016DB6ED` 进行朴素的九组三位解包，与熔丝不匹配。在解锁卡上逐个扫描 SS0 的半字节并观察哪些位发生移动，是一个直接的位映射实验。

### 2.10 训练状态与“未训练显存”理论

`FBPA_TRAINING_STATUS 0x009a0974` 在每张卡上都读为 `0x00000000`，**包括一张已经带有 64 GB CFG1 值的解锁卡**；然而，关于 80 GB 不稳定性的主流解释是上部区域没有训练，也没有对应时序。还没有人将 `TRAINING_STATUS` 与实际崩溃迹线关联起来。
**下一步：** 在过度配置档位发生崩溃前后立即读取该寄存器，并比较出厂引导和解锁引导之间的 `TIMING*_GEN` 影子寄存器。

### 2.11 80 GB 中的驻留问题与地址解码问题

针对超过 40 GB 后的失败，目前提出了两种机制，而它们预测的失败几何布局不同。驻留失败会使错误按时间和地址散布在整个上部区域；解码折叠则会在 2 的幂边界产生精确别名。观察到的折叠恰好位于 **40 GiB**，这对于驻留问题来说过于精确，因而可疑；将刷新频率加倍虽然在全部 20 个可用 FBPA 上成功写入，却没有修复不稳定性，同时损失了约 40% 的带宽。
**下一步：** 在 80 GB 几何布局、出厂时序、单 CUDA 上下文和刚刚冷引导的卡上，运行先写满再读满的折叠测试，并同时报告通过/失败结果以及失败地址的分布。
**相关但尚未解释的现象：** `cuda_memtest` 在重启后立即对全部 80 GB 通过一次，之后每次重试都失败。这个对重启的依赖是目前最具体的线索。

### 2.12 可恢复的 FBP

有些卡显示 `FBP_DISABLE 0x852`，而 `FBP_DEFECTIVE 0x840`，前者比后者多出两个仅表示禁用的位。频道内实际转储的一张 10 GB 卡则是 `DISABLE == DEFECTIVE == 0x840`，而软件覆盖实验显示，即使从 HS 进行操作，有效掩码也不会改变。
**下一步：** 在掩码不同的卡（例如 8 GB 级别的卡）上读取八个寄存器，在禁用 GSP 的 CPU-RM 模式下尝试重新启用，并检查对 `0x00820364` 的写入能否挺过一次 FLR。
**注意：** “disabled but not defective”（已禁用但没有缺陷）的晶片是否真的可以恢复，本身还没有得到证明。

### 2.13 IOMMU 与 Gen2 可靠性问题

目前存在直接矛盾的报告。多位测试者从 “still PCIe 1”（仍然是 PCIe 1）变成了在修改一次 grub 后成功，而分支安装器现在会自动设置 IOMMU；另一方面，一份独立的设置脚本把 `iommu=pt` / VT-d 列为“tested and confirmed unnecessary”（已测试并确认不需要）的配置，而它所确认的主机根本没有修改 grub。
**可以定论的证据：** 在相同软件上测试 {IOMMU off、on、pt} × {Intel、AMD} × {用户态 hammer、驱动内 `0008`} 的组合矩阵。一个看似合理但尚未演示的调和解释是：`iomem=relaxed` 只对基于用户态 `mmap` 的重训练重要，而 IOMMU 模式只在某些芯片组上重要。

### 2.14 Gen2 的重启持久性

在某些系统上，`nvidia-smi` 会在执行 `install.sh` 后立即报告 `2, 2`，而重启后报告 `1, 1`；这一现象可以复现，并且每次重新运行 `install.sh` 都会恢复为前者。
**工作假设：** 持久性取决于*打过补丁的*模块是否在引导时实际加载，而不只是被安装器在线修改。
**下一步：** 在出现失败的系统上，于重启后检查 `modinfo` 和 `dmesg`，确认是否加载了打过补丁的模块，以及是否出现 `SEC2_DEBUG: PCIe` 行，然后再判断是否应该归咎于重训练。

### 2.15 FLR 存活图中有一项尚未撤回的反对证据

有人报告几何布局在 FLR 后“every time”（每次）都会回退（2026-07-12），同一位研究者第二天又推翻了这一说法，之后 FLR 回读表和存活图重新支持了回退结论。裁决结果强烈倾向于 “FLR reverts”（FLR 会回退），但那次反转从未被正式撤回。
**下一步：** 在不加载驱动的情况下进行一次干净的 FLR，回读 CFG1、LMR 和 CSTATUS，并附上卡的 ID 发布结果。

## Tier 3：需要新能力、设备或现有人员没有的硬件

### 3.1 ECC

**想要确认：** 实现纠错。这会实质改变风险判断，也可能让边缘几何布局变得可用。
**已经尝试：** 硬件层面什么都没有做。2026-07-20 曾被直接询问，回答是 “Not yet.”（还没有）。
**阻塞机制：** `OPT_ECC_EN 0x00820228 = 0`，而 `FBPA_ECC_CTRL 0x009a0470` 中的 `MASTER_EN` 为只读。目前不知道 `MASTER_EN` 是由熔丝控制，还是由 PLM 控制；这两种情况对应的上限会完全不同。
**最便宜的第一项实验：** `FEAT_OVR_ECC` 家族（`0x0082380c`、`0x00823810`、`0x0082382c`）在打开 `0x00823804` 后原则上可写，而发布版补丁已经完成了这一步。需要测试的是，在 DEVINIT 之后写入这些寄存器究竟有没有任何效果。
**部分解决的前置问题：** HBM 堆叠本身是否携带 ECC 配置。有人读取熔丝表后提出，GA100 上的 ECC 是 HBM2 堆叠的一项特性，并以内嵌容量的形式体现；但这次读数从未与数据手册核对。A100 每个 FBPA 的 `CSTATUS_RAMAMOUNT` 读数为 `0x07ff` / `0x0fff`，而消费级部件读数为 `0x0800` / `0x1000`。如果 ECC 实际上只是厂商 QA 分档属性，那么这个问题本身就没有意义。参见[ECC](ecc.md)。

### 3.2 NVLink

**想要确认：** 真正实现解锁。**截至 2026-07-20 的总结是：“Still unsolved, a bit harder as there's no fuse mask.”（仍未解决，因为没有熔丝掩码，所以更难。）**
**两条覆盖路径都已关闭：** `CTRL_OPT_NVLINK 0x008209B8` 不会生效，因为 `FUSE_EN_SW_OVERRIDE = 0x0` 且 `FUSE_DIS_SW_OVR = 0x1`；FEAT_OVR 路径也被关闭，因为 `0x00823800`-`0x0082382C` 这一区块根本不包含 NVLink 寄存器。
**目前没有可处理的直接路线。** 以下三件成本最低的事情至少可以产生数据：

1. 在一张可以牺牲的卡上，对 `0x008209B8` 和 `0x00820820` 做一次读-写-读探测，然后重新读取 `STATUS_OPT_NVLINK 0x00820DB8`。预期结果是写入被丢弃，状态保持为 `0x00000007`。**这个阴性结果值得记录**，因为当前资料库甚至不能确定是否有人尝试过这件事。
2. 拍摄一张去掉导流罩的 170HX 高分辨率照片，覆盖设计编号 `R234`、`R236`、`R237`、`R238`、`R976`、`R1024`、`R1029`、`R1030`，并测试 NVLink 边缘金手指到 BGA 球 `F1` 和 `G1` 的连通性。这可以解决 PCB 区域是否完全贴装这一长期争议，而该问题决定绕过熔丝是否有实际意义。注意，A100 原理图**本身**将 `R237` 标记为 **NP**，因此即使是真正的 A100，也预期至少会缺少其中一个元件。
3. 插入一块实际的 A100 bridge。记录中从来没有人同时拥有一张 170HX 和一块 bridge，因此甚至还没有确认连接器是否对齐。

在第 3 项得到阳性结果前，制作 interposer 没有意义；此前虽然讨论过连接器采购、Megtron 层压板和非标准卡朝向等问题。

### 3.3 Gen4 与 DevInit 五字节编辑

PCIe Gen1 锁是位于 VBIOS MAC 范围**内部**、分布在 3 个 devinit 位置的 5 个字节，因此在不伪造 MAC 的情况下，ROM 路径已经关闭。给定一块能够重新签名的闪存，仅靠这一编辑是否可以恢复 Gen4，从未测试过；“firmware-only patch insufficient”（仅固件补丁不足够）的结论来自对熔丝值的推断，而不是一次实际补丁尝试的结果。此外，追查 Gen4 的研究者**没有支持 Gen4 的主机**，因此问题还没在技术上受阻，就已经先被硬件访问条件阻塞。
已点名但从未尝试的替代方案包括：在线缆级别伪造 TS1/TS2 Rate-ID 的 retimer interposer（Astera Aries、TI DS160PR810 类），以及修改 GSP-RM 消费 `0x57c` / `0x580` 熔丝读数位置的 GSP 补丁（跳转表位于 470.42.01 `gsp.bin` 的 `0x5D55834`，以及 580.105.08 `gsp_tu10x.bin` 的 `0x4DD9B00`）。

### 3.4 HBM 时序和 MRS 重放

**想要确认：** 找到过度配置区域的正确时序，并获得无需物理拆下散热器即可重刷、修改显存跳线的能力。
**为何写入 `TIMING*` 寄存器没有效果：** `0x9A0290` 的位 31，即 `CONFIG0.USE_TIMING_REGS`，为 **0**，因此控制器会忽略原始值，改用内部生成的值。
**为何 MRS 重放失败：** 已发布的研究报告称，所有能够由实验驱动的代理（主机、非安全模式的 SEC2、HS 中的 SEC2、PMU、非安全模式的 GSP）都无法发出一条晶片实际接受的模式寄存器设置命令。写入似乎会根据源身份被丢弃。唯一能被观察到驱动晶片的代理，是在引导时运行自身代码的 FB Falcon。
**机械操作成功，随后被阻塞：** 基线 MR1 `0x00100093`、MR2 `0x002000cf`、MR3 `0x003000ea`；派生出的跳线 7 MR1 `0x0010009b`、MR2 `0x00200029`、MR3 `0x003000ef`；重放回跳线 4 时，精确复现了引导值。随后驱动拒绝初始化并报 `RmInitAdapter failed! (0x62:0x40:2674)`。
**频道内提出但从未尝试的下一步：** 修改驱动，让它容忍变化后的状态，而不是试图让状态看起来从未被修改。
**这里所有工作的前置条件：** 从一张已知良好的 64 GB 卡和一张 10 GB 卡中，转储 HBM 自报告（IEEE 1500 区块、`0x009a3cb4`..`0x009a3cc8`）、FBPA 训练结果寄存器和 MR 寄存器。

### 3.5 L2 / LTC 解码墙

一个托管显存原子内核在分页越过 40 GB 后，会通过 UVM 原子故障路径，将 `0x17E2A0` 处的 L2 解码从 `0x70000300`（每通道 2 GB）切换为 `0x10000300`（每通道 4 GB）。该工作负载以 2 MiB 为步长，在 46 GiB 范围执行原子操作，约 0.3 s 内完成了 23,552 次原子操作。工作负载运行期间解码会保持不变，一旦上下文销毁就立即回退；触发故障还会污染上下文（CUDA error 719，然后是 Xid 45，再然后是 Xid 154）。通过一个一字节的驱动改动，可以在没有工作负载的情况下让解码保持在那里。
**为何这不是答案：** 切换该解码并不能修复超过 40 GB 的问题；遗憾的是，它位于问题的“下游”。“下游”具体指什么从来没有被确定，**这正是缺口所在**。
**下一步：** 找到能够触发同一懒惰重新启用、但不会产生故障的触发器，并刻画下游究竟阻塞了什么。

### 3.6 恢复一个 csecret

三个索引对应三种能力：**secret(6)** 可以解密 ECB 固件块（将得到 121.7 KB 的明文固件以及 Booter 代码）；**secret(2)** 可以伪造内容 MAC，一次打开 2 个 CFG1 字节和 5 个 PCIe devinit 字节，也就是解除 VBIOS 的全部 7 字节限制；**secret(0)** 是启用带 `SKIP_VBIOS_SIG` 的 HULK 证书的调试绕过。
**目前没有任何 csecret 被恢复。** 三个目标都需要电压毛刺硬件来进行差分故障分析。通过全为 `0xFF` 的已知明文预言机，已经存在一个即时离线密钥验证器，因此 DFA 行动不需要通过闪存周期来验证结果。工作量极高。

### 3.7 需要硬件编程器的 VBIOS 编辑

**2026-07-25 更新：`nvflash` 并非完全不可用。** 一个*打过补丁的* `nvflash`（omgvflash 风格）已将完整的出厂 8 GB 映像写入一张 10 GB 卡，随后又刷回原卡，过程中无需泄露版材料，也无需硬件编程器。仍然有两件事失败：**编辑过跳线的**映像会在刷写过程中触发主机侧映像检查，外来映像也无法引导。两次刷写之间没有重启，因此这次写入本身只能视为提示性证据，不能视为定论；参见[vbios.md](../hardware/vbios.md)。

这并不能证明**未签名尾部**编辑能够通过该映像检查。还没有人尝试过这种编辑。因此，带 SOIC 夹的 CH341A（以及一个 1.8 V 转接器）、拆下散热器并重新涂导热膏，仍然是下方三项编辑的假定路线；不过现在更便宜的实验，是先用打过补丁的 `nvflash` 尝试尾部编辑：

- **将 `0x45E45` 处的功耗上限从 250 W 改为 300 W。** 这个 3 字节字段当前读为 `90 D0 03`，应改为 `E0 93 04`。它位于 `0x43A00`-`0x47700` 的 15,616 字节未签名 FwSec 尾部中，因此不会破坏 MAC。自 2026-05-09 起记录为 OPEN，尚未测试。
- **`0x47177` / `0x47179` 处的 `freqDelta` 和 M0205 训练表。** 这些位置在所有 MAC 范围之外。8 GB 映像中的 `freqDelta` 为 ±1000，而 10 GB 映像中为 0，因此将 ±1000 写入 10 GB 映像，再检查是否出现核心偏移，是一个干净的自然实验。
- **在 `0xFE504` 处注入 HULK 证书。** 该槽位长度为 1113 字节，出厂状态下全为零；由于 170HX 许可区域位于 `0xFE000`，它落在 `nvflash` 写入的 1020 KB 窗口内。许可区域是否可以免于 FwSecLic 检查，从未测试过。来自 Lapsus 泄露的三个生产证书（`HULK_9970`、`HULK_12231`、`HULK_12549`）带有 `STRICT_ID_MATCH=NO`，目标为 `FUSE_FEATURE_OVERRIDE 0x823800`，并被描述为“ready to test as-is”（可以原样测试）。**任何地方都没有报告测试结果。**

### 3.8 将免驱动解锁交给出厂签名驱动

**想要确认：** 找到一种能够通过 Secure Boot 和 Windows 代码完整性检查的解锁方式。
**为何一直失败：** 出厂驱动的 booter 会拒绝 fire 操作后的 SEC2 状态，原因是两次加载后出现的“mutex horns”（`0x31` 表示互斥锁持有，`0x62` 表示 WPR2 已启用，`0x29` 来自 `0x1180f8`，因为 `mutexfree` 终止符将高半字节留在 `0xf`）。即使在几何布局一致的 10 GB 卡上也会失败，这证明被 fire 改变的是 SEC2 交接状态，而不是几何布局或写入次数。**当前发布的解锁器通过在打过补丁的驱动内部分阶段设置几何布局，绕开了这个问题。** 目前还剩两个候选根本修复方案：保留 booter 的成功路径，让 SEC2 自己启动 RTOS 并设置 DONE；或者恢复 AON `SECURE_SCRATCH` PLM 和权限状态，而后者目前只有电源域复位才能实现。

### 3.9 移植到其他晶片

- **CMP 90HX（GA102）。** 主机侧 stage 1 已完成，目标也已经明确：`FEAT_OVR_PLM 0x823804 = 0xffffff8f`（通过 `FUSE_QUADRO_WR_SEC = 1` 自封）、`FEAT_OVR_SM_SPD 0x82381c = 0x16334012`（目标值为 `0x88888888`）、`FUSE_EN_SW_OVERRIDE = 1`、`FUSE_FEAT_OVR_DIS = 0`。**阻塞点是 GA102 VBIOS 中的 SEC2 HS Booter IMEM 已加密**，所以静态分析无法得到任何结果。一份分析认为 GA102 booter 没有溢出点；相反的方案是完全不用 GA10x booter，而是在 GA10x 部件上加载 **TU10x** booter。该方案得到两份报告支持：一份称 TU10x 和 GA10x 调试 booter 使用相同的 AES-128 机密，另一份称 TU10x `booter_load` 可以在 90HX 上加载且 PLM 写入成功，不过报告者也自我限定为“1 positive test isn't enough”（一次阳性测试还不够）。值得解锁的只有算力，因为 90HX 物理上搭载 10 GB GDDR6X。
- **CMP 50HX（TU102）。** 显存访问控制寄存器集完全不同：“there is no single PLM there but there seem to be several other masks for the interesting registers.”（那里没有单一 PLM，但有意思的寄存器似乎还受到其他几个掩码控制。）
- **PG199 / DRIVE A100（`10de:20bb`）。** 即使 PLM 已打开、CFG1/LMR 写入也已生效，引导仍会在 `kflcnResetIntoRiscv 0x0` 后以 `Booter failed 0x54` 失败。没有人知道 `0x54` 是什么意思；而 `0x31`/`0x47`/`0x15`/`0x29`/`0x88`/`0x96` 这些状态码，都已经通过在 booter 反汇编中定位它们的写入位置而得到确认，相关反汇编已经掌握。名为 `PG199` 的分支**不包含 PG199 支持**。

### 3.10 NVGI 固件运行前的写入原语

SPI ROM 中的 NVGI 记录由 PBUS/XVE 的 init-from-ROM 序列器执行，发生在*任何固件运行之前*，也就是 FWSEC 打开 PLM 之前；而迄今为止对熔丝组的所有尝试，都发生在锁定后的 HS 运行时。该路径完全没有经过测试。
**其提出者本人说明的注意事项：** NVGI 只有一份副本，没有 `+0x60000` 回退，因此如果写入错误，没有 1.8 V SPI 编程器就无法恢复；它是“一个可能造成严重后果的危险工具”。
**下一步：** 在考虑任何写入之前，先从 ROM 转储中以只读方式追踪记录格式。

### 3.11 缺失的 38 个 SM

**想要确认：** 从 70 个 SM 恢复到更接近 108 个。
**已经尝试但失败：** 写入 `FUSE_CTRL_OPT_TPC_GPC`（只能移除，不能恢复）；从 HS 写入 `OPT_GPC_DISABLE`、`STATUS_OPT_GPC`、`OPT_TPC_GPC2` 和 `DIS_SW_OVR`（全部被弹回）；以及通过三种方式强制设置 `gpcMask`（`0x408970` 会重新断言为 `0xdc`，`cuInit` 会段错误）。
**频道内提出但尚未尝试的候选方案：** 通过静态熔丝裁剪掩码查询使用 GSP-RPC/RM 控制路径（`0x2080122a` / `0x2080122b`）；执行一次 GR 影子写入；或将 ROP 移植到 PMU / GSP / FECS / GPCCS。
**需要保持清醒的背景：** 在 `OPT_GPC_DEFECTIVE = 0` 的卡上，被禁用的 GPC 在物理上是完好的，因此仍有可能恢复一部分能力；但迄今找到的每条写入路径都被锁存。一张卡曾被发现通过 CTRL_OPT 裁剪到 56 个 SM，而不是熔丝下限 70 个，随后恢复了 6 个 SM，达到 62 个；这是一个*罕见*案例，其他所有被调查的卡都已经处于各自的熔丝下限。

## Tier 4：需要一次受控会话的测量争议

这些问题与其说是未知，不如说是从未在同一种方法论下得到过数字。每个问题都需要一位测试者、一张卡、一次会话，并明确说明所用工具、时钟以及 flop 计数约定。

> [!TIP]
> **已关闭：解锁后的 FP64 数值差异**
>
> FP64 曾作为 11.48 至 12.91 对比 6.3 TFLOPS 的争议列在此表中。该问题已经解决，而且从来不是计数错误。2026-07-15，一次 clpeak 转储在一张卡的一次运行中同时打印了两个数字：**FP64 非张量 6.31 TFLOPS**（`double : 6308.65`，恰好是同一次运行中 `float : 12565.14` 的一半，也就是架构上的 1:2 速率）和 **FP64 张量 11.96 TFLOPS**（`wmma_fp64`，即 8x8x4 DMMA 路径）。较高的数值来自张量路径。参见[compute-throttle.md](../unlock/compute-throttle.md)。

| 争议 | 数值范围 | 可以定论的方式 |
|---|---|---|
| HBM 带宽 | 不同来源报告 **1305.86 到 1600 GB/s**。理论峰值是 1555.2 GB/s（1215 MHz DDR × 5120-bit） | 在同一次会话中，分别对一张 8 GB 到 64 GB 的卡和一张 10 GB 到 40 GB 的卡运行同一个工具 |
| INT8 / INT4 | 已报告 44.1、50.5、276、约 280、约 300、320.2、335.6 TOPS。INT4 的测量值*低于* INT8，而 Ampere 理论上应约为其 2 倍 | 在一张记录了时钟和解锁状态的卡上，以固定形状运行一个 INT8 和一个 INT4 CUTLASS GEMM，并随内核一同发布 |
| TF32 | 七个工具报告 79 到 94 TFLOPS。出厂卡上的 TF32 是否被节流仍有争议 | 在一次会话中连续运行 torch GEMM、`gemm_probe.cu` 和 clpeak，并在一张由 `0x00823818 != 0` 确认处于锁定状态的卡上再进行一次 TF32 运行 |
| L2 缓存 | `deviceQuery` 打印 32768 KB；规格数据库写的是 8 MB；一个微基准测试独立测得 32 MB | 发布一条指针追逐延迟曲线，显示工作集从哪里开始明显下降 |
| 着色器数量 | `deviceQuery` 打印 8960 SP 和 25.27 TFLOPS；算术推导更支持 4480 和 12.63 TFLOPS（工具使用了 cc 8.6 的每个 SM 128 条 FP32 通道，而不是 GA100 的 64 条） | 算术已经基本定论；之所以仍记录，是因为没有任何来源通过实验解决它 |
| 显存时钟 | 出现过 304、364、432、864、1215、1458、1728 和 1890 MHz。不同工具使用不同的时钟域和倍频，而且没有人说明换算方式 | 一张卡、一次会话：同时捕获 `nvidia-smi -q -d CLOCK`、mixbench 和带宽扫描，并记录 VBIOS 版本 |
| `clocks.max.sm = 1935 MHz` | 这是一个报告字段，不是工作时钟。所有持续测量都停在 1410 MHz（`-pl 300` 时为 1470 MHz），VBIOS 表中的最大值是 1695 MHz | 在第二张卡上重新检查一次 |
| 单卡 27B 解码 | vLLM 上报告过 97、90、75 和 58.5 t/s，另有 llama.cpp Q4_K_M 的 36.87 t/s；它们使用了不同的后端、量化方式、MTP 状态、上下文长度和 vLLM 版本。每个数字都只来自一份报告 | 完全按一个已发布仓库的配置运行，并贴出命令行标志 |
| PCIe 敏感性 | 位宽几乎没有影响（单卡仅 +2%），而代数影响很大（3 卡流水线并行 prefill +44%） | 在一台机器、一个模型上，测试 {Gen1、Gen2} × {x4、x16} 的 2x2 矩阵 |
| 空转功耗 | 27 W 到 46 W。已知混杂因素包括卡的变体、晶片温度（漏电反馈），以及 CUDA 上下文是否让模型驻留（约 +12 W） | 一张卡、一台主机，在三个受控晶片温度下，分别记录有无驻留上下文时的空转功耗 |
| 长期稳定性 | 最长的已验证干净运行包括跨四张卡的 2 小时压力测试、一次 10 分钟 cuBLAS 运行，以及 1-2 天 LLM 运行的二手报告。一次 24 小时运行和一次 48 小时运行都曾启动，但从未公布结果 | 发布这些运行结果 |

## 需要 X 光、去盖或卡尺才能回答的物理问题

- **封装上有多少个 HBM 堆叠，分别来自哪家厂商？** 一张去盖的 8 GB 卡肉眼可见六个堆叠，十二个 FBP 中有四个被熔丝裁剪；一位晶片照片来源称六个堆叠中有两个是空壳；第三种读数则只有四个堆叠。三种说法都预测出同一个实测的 4096-bit 总线宽度，因此总线宽度无法区分它们。流传的一份指南反而声称是五个 16 GB 堆叠，这将意味着 5120-bit 总线，与测量结果不符。当前较强的工作假设（8 GB 使用 SK hynix，10 GB 使用 Samsung）从未通过封装标记、X 光或厂商 ID 读数验证。**注意，几何布局不依赖这个问题：** 无论哪种情况，CFG1 配置档位都相同。
- **R240/R241（DEVID_SEL）在板上的什么位置？** 之所以想确认，是因为驱动正是根据设备 ID 选择几何布局，而 `OPT_DEVID_SW_OVERRIDE_DIS = 1` 关闭了所有软件路径。当前的搜索启发式是合理的：在承载小于 500 的设计编号的 PCB 一侧、200 系列设计编号区域内，寻找一个紧挨空焊盘的电阻；但这个方法还没有在大量样本上验证。两位研究者对于候选区域究竟靠近 R986-R1005，还是在另一面，意见不一。
- **导热垫是 1.5 mm 还是 2 mm？** 一次测量来自打开过卡的持有者，另一次只是别人说的 “I think”（我觉得）。用卡尺即可定论。
- **未贴装的 4-pin 导流罩焊盘真的是风扇接口吗？** 有一份报告称其上存在 12 V 和地，但没有测到转速计或 PWM；同一讨论中的一位怀疑者说它看起来不像风扇连接器。没有照片确认的引脚定义，也没有成功接入风扇的先例。

## 从现有记录无法回答

- **总产量。** 估计范围从 10k 到几十万不等。已发布的估计，是用 FY2022 CMP 收入除以假定的平均售价来推算单元数量，且没有按型号区分销售组合。公开资料中不存在按型号统计的发货数据。诚实的答案是：没有任何可靠数字。
- **2026-07-05 那条将 Gen2 视为已解锁的消息。** 它比复现结果早了整整三周，并且直接与 2026-07-07 一条称 “We still need something for PCIe 2.0”（我们仍需要为 PCIe 2.0 做点什么）的消息冲突。它要么来自一项从未传播开的更早独立结果，要么是时间戳被错误归属。只有原始消息的元数据能够定论。该消息的技术内容（Gen3 受熔丝控制）与其他所有证据一致，因此可以采信；但日期不能采信。
- **已发布工具是否符合净室自身的规则。** 发布载荷中的每一个常量，都可以从早于泄露工件、且带有日期的公开材料中独立推导出来；净室工作也早在几天前就发布过一条等价链。同样真实的是，发布代码在泄露工件出现 70 分钟后出现，其中移除了一处敌对改动，并增加了一个设备 ID 分支。“原则上可以推导”不等于“事实上就是这样推导出来的”。记录中没有任何东西能够定论这一点；参见[净室与来源溯源](../history/clean-room-and-provenance.md)。
- **泄露包究竟是泄露所得，还是独立重新实现。** 接近这项工作的人分别持有这两种观点；无论是哪种情况，该工件在功能上都等价。
