# VBIOS：结构、版本与 DEVINIT

**本页涵盖以下内容。** CMP 170HX SPI ROM 映像的布局；如何在不把卡刷成砖的情况下转储它；各个区域分别包含什么；哪些部分受到密码学保护、哪些没有；DEVINIT 是什么、它控制和不控制哪些内容；按批次整理的版本清单；以及按可修改性排序的目标列表。

**首要结论：社区解锁完全不接触 VBIOS。** 发布版 `cmpunlocker` 工具从不读取、写入、刷写或解析 ROM。仓库中没有 `nvflash`，没有 SPI 访问，也没有任何映像处理；整个工具只有六个内核模块补丁，以及 `install.sh` 和 `remove.sh`。对发布版代码树搜索 *flash*、*nvflash*、*spi*、*rom* 和 *vbios* 的完整单词，没有任何命中；唯一的子串命中都是偶然情况，例如 `remove.sh` 完成横幅中的 "from"。解锁发生在运行时，位于打过补丁的 GSP 引导路径内部。参见[解锁如何工作](../unlock/how-it-works.md)。

第二个首要结论是：**这张卡上有意设置的 VBIOS 级限制，总共只有七个字节。** 其中两个字节是 CFG1 跳线 4 的寻址档位（从 `44` 到 `66`），控制 HBM 寻址深度、使用 12 位还是 14 位行地址，以及每个 HBM2 堆叠可寻址 2 GB 还是 8 GB；另外五个字节属于 PCIe 速度 DEVINIT，分布在三个位置。这两部分都位于 MAC 验证范围内，因此都需要一把目前无人拥有的密钥。170HX ROM 与 A100 ROM 的其余差异，都是零散的设备 ID 引用和按构建生成的训练校准数据，与限制本身无关。

## 快速了解

| 问题 | 答案 |
|---|---|
| 量产 ROM 大小 | 每一份 GA100 量产转储都是 1,044,480 字节（1020 KB） |
| 偏移量 0 处的魔数 | `NVGI` |
| 运行时读取窗口 | BAR0 + `0x300000` 处的 NV_PROM |
| 受密码保护的范围（170HX 250 W） | `0x2200`-`0x43A00` |
| 保护类型 | 对称 MAC（Davies-Meyer 哈希 + AES-KDF），密钥在 csecret(2)，**不是** RSA 映像签名 |
| 可自由修改 | `0x43A00` 到映像末尾（未签名 FwSec 尾部、填充、备份镜像、InfoROM） |
| VBIOS 版本影响解锁吗？ | 不影响 |
| 能刷入修改过的映像吗？ | 不能，`nvflash`/`omgvflash`/`nvflashk` 都不行。修改未签名尾部需要 CH341A |

## 转储 VBIOS

> [!CAUTION]
> **动手前务必先转储**
>
> 绝大多数失败刷写或损坏映像，**只有事先保存了出厂 ROM 才能恢复**。曾经把这些卡刷成砖、后来又成功恢复的人反复建议：保留出厂转储，并且在接触 NVGI 区域**之前**准备好外部 SPI 编程器。一位研究者曾说“如果我损坏了 NVGI，就完全没有恢复路径”，随后在一分钟内自行更正：使用硬件 SPI 编程器即可恢复。NV_PROM 的 MMIO 转储可以作为足够可靠的备用映像。参见[恢复](../procedures/recovery.md)。

共有三种转储路径。它们捕获的字节范围不同，可能出现的失败模式也不同。

| 方法 | 捕获的范围 | 需要 | 风险 | 备注 |
|---|---|---|---|---|
| `nvflash --save` | 1020 KB（`0x00000`-`0xFF000`） | 驱动已绑定、root | 低 | 标准路径。在 170HX 上，这个窗口**确实**包含 `0xFE000` 处的许可区域；A100 则不包含，因为 A100 的许可 TOC 位于 `0xFF000` |
| NV_PROM MMIO 回读 | 从 BAR0 + `0x300000` 开始的 1,044,480 B | root、BAR0 映射 | 极低，只读 | 这是显卡自己看到的 ROM 视图。净室逆向工具 `ga100_topology_report.py` 使用此方法。某些位置可能显示 `0xFF`，而 SPI 转储会显示实际内容（见下方注意事项） |
| CH341A + SOIC 夹 | 整个 SPI 芯片 | 拆下散热器、重新涂导热膏 | 物理风险 | 唯一能够*写入*修改后映像的路径。出厂卡带有硬件写保护 |

### 先识别显卡和 VBIOS

```bash
lspci -nn -d 10de: | grep -i GA100
# 0d:00.0 3D controller [0302]: NVIDIA Corporation GA100 [CMP 170HX] [10de:20c2] (rev a1)

nvidia-smi --query-gpu=vbios_version,pci.device_id,pci.sub_device_id,memory.total \
           --format=csv
```

`10de:20c2` 对应 8 GB SKU，`10de:2082` 对应 10 GB SKU。完整的识别矩阵见[板卡与变体](board-and-variants.md)。

### `nvflash` 保存

```bash
sudo nvflash64 --save stock_$(date +%F)_$(hostname).rom
sha256sum stock_*.rom
```

### 通过 BAR0 回读 NV_PROM

运行时可以通过 **BAR0 + `0x300000`** 处的 NV_PROM 窗口读取 SPI 闪存，长度为 1,044,480 字节，前四个字节是 `NVGI`。该窗口基址由 FWSEC 反汇编推导得出。

```python
#!/usr/bin/env python3
# 只读 NV_PROM 转储。需要 root。把 BDF 换成你卡的。
import mmap, os

BDF   = "0000:0d:00.0"
BAR0  = f"/sys/bus/pci/devices/{BDF}/resource0"
PROM  = 0x300000          # NV_PROM 孔径在 BAR0 内的偏移量
SIZE  = 1044480           # 1020 KiB

fd = os.open(BAR0, os.O_RDONLY)
m  = mmap.mmap(fd, PROM + SIZE, mmap.MAP_SHARED, mmap.PROT_READ)
rom = m[PROM:PROM + SIZE]
assert rom[:4] == b"NVGI", f"bad magic: {rom[:4]!r}"
open("vbios_prom.rom", "wb").write(rom)
print(f"wrote {len(rom)} bytes")
```

> [!WARNING]
> **MMIO 回读不一定与 SPI 转储一致**
>
> 在 Drive A100 上，NV_PROM 回读在 `0xFE000` 和 `0xFF000` 两处都显示全 `0xFF`。目前尚不清楚该部件上的区域是否确实为空，还是 TOC 结构无法通过 NV_PROM 路径正常呈现。任何通过 MMIO 调查许可区域的人，都应先用 SPI 转储确认，再判断某个区域是否为空。

### 使用 CH341A 转储并验证

```bash
# 独立读取两次并比较。不要相信单次夹子读取。
flashrom -p ch341a_spi -r spi_dump_1.rom
flashrom -p ch341a_spi -r spi_dump_2.rom
cmp spi_dump_1.rom spi_dump_2.rom && echo "clip contact is good"
```

在出厂卡上，SPI 闪存受到硬件写保护：转储得到的状态寄存器值为 `00000000 (0x00)`、`01000000 (0x40)`、`11111111 (0xFF)`。一位测试者在遇到这个保护后十分钟内就绕过它并完成了一次刷写，因此它是障碍，不是绝对屏障。

> [!CAUTION]
> **重新上电前恢复写保护**
>
> 刷写失败 `0xBADF3000` 且板卡无法读取闪存，原因是上电前**没有**重新启用 SPI 写保护。恢复方法是用芯片夹直接重刷 SOIC，然后重新设置写保护。相关症状是 RM 初始化适配器失败。这块板不存在 OS 级别的闪存写入路径。

### SKU 与完整性指纹

对固定范围计算两个截断的 SHA-256 值，可以用作低成本的 SKU 和完整性检查。对于同一 SKU，已经检查过的每份映像中的这两个值都逐字节一致；因此出现不匹配时，说明 VBIOS 的代码存在差异，而不只是每张卡的单元数据不同。

```bash
IFR()  { dd if="$1" iflag=skip_bytes,count_bytes skip=0        count=$((0x1000))          status=none | sha256sum | cut -c1-16; }
FW()   { dd if="$1" iflag=skip_bytes,count_bytes skip=$((0x1200)) count=$((0xC1000-0x1200)) status=none | sha256sum | cut -c1-16; }
echo "IFR      $(IFR vbios_prom.rom)"
echo "FIRMWARE $(FW  vbios_prom.rom)"
```

| SKU | IFR `0x000000`-`0x001000` | FIRMWARE `0x001200`-`0x0C1000` |
|---|---|---|
| 10 GB（`0x2082`） | `3ca3d24230d6800f` | `8c4e1344c51b0940` |
| 8 GB（`0x20C2`） | `2ff19960f9175320` | `e2c91c1808ae2759` |

上面的归属由三份报告对一份报告裁定；唯一的离群报告把 8 GB 的配对值标到了 10 GB 映像上，因此被视为抄写错误。只要在拓扑工具的一次运行中并排展示两个 SKU 的输出，就可以最终确认这一点。

## 区域布局

已发布的分析将其称为 13 区域图（仅计算内容区域）。这里把填充、镜像和 InfoROM 也纳入其中。大小取自 170HX 250 W 映像；“已签名”表示位于 `0x2200`-`0x43A00` 的 MAC 验证范围内。

| 偏移量范围 | 内容 | 大小 | 已签名 |
|---|---|---|---|
| `0x00000`-`0x02200` | NVGI 头 + RFRD 清单，明文 | 8.5 KB | 否（位于签名起点之前） |
| `0x02200`-`0x05E00` | PciAt 区域、BIT 令牌、PERF_PTRS | 15.0 KiB | **是** |
| `0x05E00`-`0x0C700` | FwSec 头、VN 映像 1 和 2、NPDS/NPDE | 27 KB | **是** |
| `0x0C700`-`0x0C800` | NPDS/NPDE 头 | 256 B | **是** |
| `0x0C800`-`0x13E00` | 压缩的 Falcon 代码，与 A100 在 delta 0 处共享 87% | 29.5 KB | **是** |
| `0x13E00`-`0x14A00` | 区域间空隙，包含零和头部 | 3 KB | **是** |
| `0x14A00`-`0x20000` | 加密固件区域 A，AES-128-ECB | 45.5 KB | **是** |
| `0x20000`-`0x20700` | DMAP 明文空隙，包含 `"Mar  5 2021"` 构建字符串和 Falcon fuc5 代码 | 1.8 KB | **是** |
| `0x20700`-`0x33800` | 加密固件区域 B，AES-128-ECB | 76.2 KB | **是** |
| `0x33800`-`0x41200` | 配置 / DEVINIT 类表，Shannon 熵为 4.5-6.0 | 54.5 KB | **是** |
| `0x41200`-`0x42A00` | 跳线和训练表；CFG1 跳线 4 的档位字节在 `0x41D53` | 6 KB | **是** |
| `0x42A00`-`0x43A00` | 尾部零值 | 4 KB | **是**（在此边界结束） |
| `0x43A00`-`0x47700` | **未签名 FwSec 尾部** | 15,616 B | 否 |
| `0x47700`-`0x60000` | `0xFF` 填充 | 100 KB | 否 |
| `0x60000`-`0xA7700` | **`0x00000`-`0x47700` 的备份镜像** | 285 KB | 否 |
| `0xA7700`-`0xC0000` | `0xFF` 填充 | 100 KB | 否 |
| `0xC0000`-映像末尾 | InfoROM（1020 KB 转储里在 `0xFF000`，完整 1 MiB MMIO 回读里在 `0xFFFFF`） | 252-256 KB | 否 |

偏移 `+0x60000` 的镜像解释了对比工作中所有重复出现的表地址：如果某张表同时出现在 `0x41D41` 和 `0xA1D41`，那是同一张表及其备份副本，而不是两张不同的表。

> [!NOTE]
> **“NVGI 区域”有两种不同含义**
>
> 上面的区域图将 `0x00000`-`0x02200` 称为 NVGI。8 GB 与 10 GB 的差异分析则把 `0x00000`-`0x05E00` 都称为 NVGI，因此位于 `0x2CBF`、`0x38BA`、`0x595C` 和 `0x5AF8` 的四个 MAC 块，虽然在 `0x2200` 之上，仍会被描述为“位于 NVGI 内”。

### NPDS 主体组成

NPDS 主体 `0x0C700`-`0x43A00`（226,048 字节）按熵类别分解如下：

| 类 | 占比 | 详情 |
|---|---|---|
| AES-128-ECB 密文 | 121.7 KB（54%） | 两个区域、同一把密钥、101 对内部重复块 |
| DEVINIT 类配置表 | 54.5 KB（24%） | 熵为 4.5-6.0，结构化明文 |
| 压缩的 Falcon 代码 | 29.5 KB（13%） | 与 A100 在 delta 0 处共享 87% |
| 头部、空隙、跳线表、填充 | 20.3 KB（9%） | 明文 |

正是这 24% 的明文配置区域，使得 DEVINIT 字节可以通过模式搜索定位，而加密的 FwSec 固件无法这样处理。

## RFRD 清单与签名范围

MAC 验证范围不是推测出来的，而是由映像明确声明的。`0x2000` 处的清单是**映像布局描述符**，不是功耗表。

| 偏移量 | 字段 | 值 / 含义 |
|---|---|---|
| `0x2000` | 魔数 | `"RFRD"` |
| `0x2004` | u16 清单版本 | `3` |
| `0x2008` | u32 `pci_option_rom_offset` | 指向 PciAt 映像起点 `0x5E00` |
| `0x200C` | u32 `pci_option_rom_size` | **MAC 验证范围的大小** |
| `0x200D` | （字节） | `pci_option_rom_size` 的高字节。修改它会使声明的大小与实际签名内容不同步，从而导致 MAC 验证失败 |
| `0x201C` | u32 `secondary_base` | `0x2200` |

签名内容始终从 `0x2200` 开始。各映像如下：

| 映像 | field_0C | MAC 验证范围 |
|---|---|---|
| 170HX 8 GB 和 10 GB，250 W | `0x00041800` | `0x2200`-`0x43A00`（268,288 B） |
| 170HX 300 W | `0x00041A00` | `0x2200`-`0x43C00` |
| A100 PCIe 40 GB | `0x00042200` | `0x2200`-`0x44400` |
| Drive A100 32 GB | `0x00058A00` | `0x2200`-`0x5AC00` |

### 该范围由实测确定，而不只是从字段中读出

2026-05-08 的四次实体 CH341A 刷写周期最终确定了这个范围。在声明范围*之外*写入 `0xFF` 填充后，显卡可以正常启动，驱动也能正常加载；而在 `0x2200`-`0x43A00` 窗口*内*修改一个字节，就会使 Booter 卡死。GA100 上典型的 MAC 损坏失败特征是：

```text
GFW_BOOT = 0x401    （或 0x001）
```

单字节测试是在 CFG1 档位字节 `0x41D53` 处进行的，恰好是显存解锁需要修改的位置。这证明了“修改 MAC 范围内的内容不可行”。

## 密码学机制

这里有两把不同的密钥和两种不同的机制，但经常被混为一谈。

| 机制 | 覆盖 | 密钥 | 状态 |
|---|---|---|---|
| 对称 MAC，Davies-Meyer 哈希 + AES-KDF | `0x2200` 到范围末尾的内容 | csecret(2)，保存在 SCP 硬件中 | 伪造需要密钥；据称只能通过 DFA 硬件攻击提取 |
| AES-128-ECB | 两个 FwSec 固件区域 | csecret(6) | 每个 GA100 变体同一把密钥 |
| RSA | 引导 ROM 认证 Booter 代码 | NVIDIA 量产 | 独立的机制，常被误认为映像签名 |

### AES-128-ECB：三方面的证据

1. **跨 ROM 重新收敛。** 13 次匹配运行中，170HX 与 A100 的 2,667 个块有 442 个相同。明文出现差异后，CBC 永远不可能重新收敛。
2. **内部重复块**（“ECB 企鹅”）。170HX 映像内部有 24 对重复的 16 字节块，A100 映像内部有 28 对。这排除了 CTR。
3. **严格的 16 字节对齐。** 将比较位置错开一个字节后，匹配数会从 442 降到恰好 0。

**所有 GA100 变体的 FwSec 块都由同一把密钥加密。** `0x14A00` 处的前四个 ECB 块，在 170HX 8 GB、170HX 10 GB、170HX 300 W 和 A100 PCIe 上逐字节一致。Drive A100 于 2026-05-31 加入比较：它有 30 次 ECB 预言命中，前四个块也相同，并以 `b2a93eaa0300209b` 开头。只要恢复一次 csecret(6)，就能解密现有的每一份 GA100 VBIOS。

### 免费的已知明文预言机

ROM 包含明文全部为 `0xFF` 的填充块，因此得到：

```text
AES_ECB(key, FF x 16) = 717d1494 eaca317f f1061952 58b38377
```

重复的密文块位于 `0x1F8F0` 和 `0x1FB60`（在 ImHex 中标记为 "end of imem_sec"）。ECB 区域 A 中有 21 个这样的填充块，区域 B 中有 13 个，而且这一模式会在所有 ROM 变体中重复出现。因此，可以不经过刷写周期，在几微秒内离线验证候选密钥，这正是 DFA 行动具备可行性的关键。

同一个 128 位值还标识着**使用简单的非机密密钥 `01234567...` 加密的调试构建 Falcon IMEM 段**。研究 DEVINIT/FWSEC 的推荐流程是：从公开合集获取一份 VBIOS，搜索该填充模式，用简单密钥解密对应的 IMEM 段，再为反汇编结果添加注释。这是多位专家一致提出的建议，但频道内目前还没有人贴出结果。

> [!NOTE]
> **未解问题**
>
> 另有一种说法称“密钥在 NVIDIA 自己的网站上，我觉得是 debug #37”，但从未得到证实。密钥本身和解密后的量产映像都没有被公开。`01234567...` 调试 IMEM 的方法可以视为可执行方案，而“debug #37”只能视为未经验证的说法。

## 映像中的表

### 位于签名范围内（仅具文档价值）

| 表 | 偏移量 | 备注 |
|---|---|---|
| BIT 表 | `0x5EB0`，16 个令牌 | 六份量产 ROM 的偏移和令牌数量都相同 |
| FwSec NPDS 设备 ID | 位于 FwSec 头部 | **七份**映像都声明为 `0x2080`（通用 GA100），与各自的 PciAt 设备 ID 无关 |
| CFG1 / HBM2 跳线表 | `0x41D41`（170HX 8 GB、10 GB、"16 GB"），备份位于 `0xA1D41` | 16 个 32 位字，**未按字对齐**；次要 `strap_info` 表位于 `0x6A09` |
| CFG1 跳线 4 档位字节 | `0x41D53`（250 W）/ `0x41F53`（300 W） | 七字节限制中的两个字节 |
| PCIe 速度 DEVINIT | `0x33800`-`0x41200` 内三个位置上的 5 个字节 | 七字节限制中的另外五个字节 |

各映像的跳线表偏移量：

| 映像 | 版本 | 主 | 备份 |
|---|---|---|---|
| 170HX 8 GB 和 "16 GB" | `92.00.67` | `0x41D41` | `0xA1D41` |
| 170HX 10 GB | `92.00.66` | `0x41D41` | `0xA1D41` |
| 170HX 300 W | `92.00.6D` | `0x41F41` | `0xA1F41` |
| A100 PCIe 40 GB | `92.00.90` | `0x4285A` | `0xA285A` |
| A100 SXM4 40 GB | `92.00.45` | `0x419E5` | `0xA19E5` |
| Drive A100 32 GB | `92.00.A0` | `0x3A7D2` | 未确定 |

300 W ROM 将整组表放在 250 W 同系列映像之后恰好 `0x200` 字节处。泄露的 GA100 仿真/模拟 ROM 使用完全不同的约 230 KB 布局，两份副本位于同一映像中的 `0x0864C` 和 `0x1AD72`，因此其中没有任何内容可以直接移植。

**档位字节解码。** 每个 32 位跳线字的第三个字节是一对档位半字节，取值为 `44`、`55`、`66`、`77`，分别编码每个 HBM2 堆叠可寻址的 2 GB、中间档位、8 GB 和 16 GB。大多数条目采用填充模式 `00 90 66 22`。在 10 GB VBIOS 中，只有跳线 4 被降到 `44`；在 8 GB VBIOS 中，跳线 5 和 7 也被降档。跳线 4 是 10 GB 卡使用的物理跳线，跳线 7 则对应 8 GB 卡。这与运行时解锁写入 `0x009a0204` 处 CFG1 的档位编码相同；参见[显存几何布局](../unlock/memory-geometry.md)。

> [!NOTE]
> **未解问题**
>
> 2026-07-25，短短几小时内出现了两种互不兼容的逐跳线 HBM 部件字段解码。**厂商和修订字段是一致的**（Micron/Samsung/Hynix，rev1/rev2/rev3/rev6/rev10）；**每晶片容量和堆叠高度字段则不一致**（例如将跳线 5 解码为 `Hynix_rev6_16Gb_org0x4`，或 `Hynix_rev6_8Gb_4H_org0x4`）。第二种解码的作者指出，公开流传的论坛解码脚本“并不完全适用于 HBM 显存配置”。`44`/`66`/`77` 的容量映射没有争议。要解决这个问题，需要权威的字段宽度定义，或者将某条解码结果与已通过物理方式识别的 HBM 堆叠料号对应起来。

### 位于签名范围外（实际可编辑）

从 `0x43A00` 开始的所有内容都未签名，可以用 SPI 编程器自由修改；它们与已经成功启动的 `0xFF` 填充测试属于同一类。

| 条目 | 偏移量 | 值 / 详情 | 状态 |
|---|---|---|---|
| 板卡功耗上限 | `0x45E45`，3 字节 | `90 D0 03` = 250 W；若改为 300 W，则为 `E0 93 04` | 位于 MAC 外。**开放，自 2026-05-09 起未测试** |
| `NV_FUSE_CTRL_OPT_*` 表 | `0x47341`，25 项 | 在探测过的 13 张 GA100 卡上全为零 | 位于范围外。语义未确定 |
| `freqDelta` | `0x47177` / `0x47179` | 8 GB 映像为 ±1000，10 GB 和 A100 映像为 `0` | 位于范围外。解释了核心偏移为何只在 8 GB 卡上有效 |
| M0205 显存训练表 | `0x467f8`（10 GB）/ `0x469f8`（检查过的另一份映像） | 头部为 `ver=0x10 hdr=8 entsz=1 cnt=1`，原始值为 `10 08 01 01 10 07 00 00`，包含 16 个 7 字节跳线子条目 | 位于范围外 |
| InfoROM | `0xC0000` 向上 | 完全未签名 | 位于范围外 |
| 许可 / HULK TOC | `0xFE000`-`0xFEFFF` | 见下文 | 位于范围外 |

检查过的两份映像中，M0205 跳线子条目逐字节相同。例如：strap0 为 `0f ff ff ff ff ff ff`，strap2 为 `ff ff ff 0f ff ff ff`，strap4 为 `ff ff ff ff ff ff 0f`，strap7 为 `ff ff 0f ff ff ff ff`，strap9 为 `ff ff ff ff ff 0f ff`，strap12 为 `ff 0f ff ff ff ff ff`，strap14 为 `ff ff ff ff 0f ff ff`；除 7 和 9 之外，所有奇数跳线都为全 `ff`。

**根据上述偏移量和 MAC 边界可以推导出：**2026 年 7 月读出的每张显存相关表（`freqDelta`、M0205、CTRL_OPT）都位于 `0x43C00` 之上，因此在所有 170HX MAC 范围之外；而位于 `0x41D41`/`0x41D53` 的 CFG1 跳线档位表，距离边界约 10 KB，处于范围之内。**这是一条清晰的分界线：映像中的显存时序和时钟偏移可以编辑，显存容量跳线则不能。**

> [!NOTE]
> **未解问题**
>
> 未签名尾部的显存修改是否真的会生效？最直接的实验是在 10 GB 映像中把 `±1000` 写入 `freqDelta`（该映像中的值为 `0`），观察是否出现核心偏移。在一张已经保存出厂转储的卡上进行一次 CH341A 刷写即可回答这个问题。目前没有人报告尝试过。

### 许可区域与 HULK 槽

**170HX 的许可区域位于 `0xFE000`-`0xFEFFF`，而不是 `0xFF000`。** 这纠正了整个社区从 A100 沿用下来的假设。结论由通过三种方法获得的五份独立 170HX 转储共同验证：其中包括三份 10 GB 转储（一份来自 SPI、一份来自 MMIO），以及两份 8 GB 转储。在每一张 170HX 上，`0xFF000` 处顶部的 4 KB 都是全 `0xFF`，未被使用。这一点很重要，因为 `nvflash` 在 170HX 上会转储 1020 KB，所以该区域确实位于这张卡的 nvflash 窗口内；而在 A100 上则不在。

| 偏移量 | 内容 |
|---|---|
| `0xFE000` | 8 个零字节 |
| `0xFE008` | `"LU"` + `00 10 00 00 00 01`：区域头部，大小 `0x1000`，版本 1 |
| `0xFE010` | 槽表：`"LIC" 01 00 1D 00`（LIC 位于 +0x1D）、`"ULF" 1D 00`（解锁标志）、`"UPR" 7D 04`（解锁参数位于 +0x47D）、`"HLK" ED 04`（HULK 证书位于 +0x4ED）、`"ULF" 01 00 60 04` 终止符 |
| `0xFE48D` | UPR 槽头部，载荷为空 |
| `0xFE4FD` | HLK 槽头部 `"HLK" 01 00 60 04`，版本 1，标志为 0，槽大小 `0x0460`（1120 B） |
| `0xFE504` | HLK 载荷，容量为 1113 字节，**出厂 170HX 上全为零** |

推断是：预先建立但为空的 HULK TOC，意味着 FWSECLIC 会在每次启动时扫描许可区域。否则，如果没有任何组件读取它，NVIDIA 没有理由随卡交付完整的槽表和一个 1120 字节的保留槽。由此推测，在 `0xFE504` 放入伪造的或量产签名的 HULK 证书，可能成为一条解锁路径。不过，这一推测从未通过对 FWSECLIC 加插桩得到演示。

> [!NOTE]
> **未解问题**
>
> 在 `0xFE504` 注入 HULK 证书。这个槽确实存在，容量为 1113 字节，出厂状态全为零，而且位于 `nvflash` 的写入窗口内，因此原则上不需要 CH341A。这里有两个障碍：同一份分析指出，即使修改未签名尾部，`nvflash` 也会被 FwSecLic 的写入时验证拦截；许可区域是否属于例外从未测试过；此外没有人拥有签名证书。成本最低的下一步，是向 HLK 载荷写入任意非零模式，观察写入是否被接受，从而区分“区域可写”和“需要有效证书”这两个问题。

### InfoROM

完全未签名。值得注意的标签包括：`IMG` 容器头、`BRD` 板卡信息 / 料号、`OBD` 卡名、`PPO` 功耗/性能（**所有 170HX ROM 中都为空**）、`BBX` BlackBox 遥测、HBM RAS 的行重映射 `RPR`，以及 ECC 配置 `ECC`（**仅 A100 有**）。卡名字符串包括 `"NVIDIA-A100-PCIe-40GB"`、`"NVIDIA A100-SXM4-40GB"` 和 `"CMP 170HX"`。

一张正在运行的 10 GB 卡会枚举 **17 种不同的对象类型**：APP、BBX、BRD、DEM、IMG、NEN、NVL、OBD、OCT、OEM、OMS、PPO、ROM、RPR、RRL、SEN、ULF；对应版本为 APP v6、BBX v4 和 v6、BRD v2、DEM v6、IMG v2、NEN v14、NVL v6、OBD v2、OCT v6、OEM v2、OMS v14、PPO v6、ROM v2、RPR v6、RRL v6、SEN v14、ULF v0。同一 SKU 的 `nvidia-smi` 报告 Inforom Image Version `1001.0105.01.02`、OEM Object 2.0，ECC Object 和 Power Management Object 都为 N/A；这与 `ECC` 仅存在于 A100、`PPO` 为空的情况一致。

> [!WARNING]
> **不要用 InfoROM 对象总数作为显卡指纹**
>
> 22、23 和 28 这几个总数都曾被报告过，而且**全部正确**：BBX 和 DEM 是会随着运行时活动累积的遥测记录。只有 17 种不同类型以及各对象的版本具有结构意义。

## DEVINIT

DEVINIT 是驻留在 VBIOS 中的初始化脚本，会在启动时编程 GPU 寄存器，早于驱动发现设备。在 GA100 上，它位于 `0x33800`-`0x41200` 的配置区域中：这里是结构化明文，熵为 4.5-6.0。因此可以通过模式搜索定位 DEVINIT 字节，却无法用同样的方法定位加密的 FwSec 固件。**由于该区域在 `0x41200` 结束，远低于 `0x43A00` 的 MAC 边界，所以任何 DEVINIT 修改都会破坏 Booter 的 MAC。**

### 它在哪里运行

闭源 NVIDIA RM 包含一个 **x86 DEVINIT 脚本解释器，符号为 `_nv000358rm`**，通过 ASCII 操作码分派。它在代码地址 `0x264fb1` 读取跳线寄存器 `0x101000`，并以通用方式执行 VBIOS DEVINIT 寄存器写入。因此，L2 解码寄存器 `0x17e2a0` 从不会作为立即数出现在 RM 代码中：它的地址来自 VBIOS 脚本流，而不是 RM。以下三个注册表键控制 DEVINIT 的运行位置：

| 注册表键 | 作用 |
|---|---|
| `RMExecuteDevinitOnPmu` | 在 PMU 上运行 DEVINIT |
| `RmDisableFbflcnDevinitBoot` | 禁用 FBFLCN DEVINIT 引导路径 |
| `RMDevinitBySecureBoot` | 通过安全启动运行 DEVINIT |

置信度为中等：结论来自包含具体符号和偏移量的二进制分析，但尚未被独立复现。

### 启动顺序

```text
NVGI 记录执行
  -> IFR ucode 取 FWSEC 描述符并启动 FWSEC
  -> FWSEC 拉起 PLM
  -> devinit / UDE08 编程全部 29 个 FBPA 寄存器
  -> FBFLCN 训练 HBM
```

由此直接得到两个后果，而它们都堵住了明显的攻击方向：NVGI 写入 MR1/MR2/MR3 的任何值，都会在稍后被 DEVINIT 根据启动跳线的表值覆盖；从 NVGI 降低 PLM 也没有意义，因为 FWSEC 随后会再次提高它们。置信度为中等；这是根据固件分析得到的执行顺序推论，而不是实测结论。

### DEVINIT 与 PCIe Gen1 锁

PCIe 速度限制由**三个 DEVINIT 位置上的 5 个字节**组成（Gen1 对比 Gen3/4），全部位于 MAC 范围内。因此，ROM 修改路径与显存跳线字节一样不可行：没有 csecret(2)，就无法伪造 MAC，也无法启动。

取代 ROM 修改的是纯运行时方案。未发布的 `Gen2` 系分支通过打过补丁的驱动写入 PCIe 寄存器，达到 Gen2（5 GT/s），完全不接触 ROM；结果为 `LnkCap max Gen2 0x00456102`、`LnkCap2 0x00000006`、`LnkSta trained Gen2 x4 0x1042`，以及 `nvidia-smi` 的 cur/max/width `2,2,4`。这里改变的只是链路**速度**；链路**位宽**是独立的、完全由物理条件决定的因素。参见[PCIe Gen2](../unlock/pcie-gen2.md) 和[PCIe 子系统](pcie-subsystem.md)。

> [!NOTE]
> **未解问题**
>
> Gen3 和 Gen4 仍然无法达到。每一张被探测的 170HX 上，`FUSE_PCIE_GEN23_DIS` `0x0082057c` 和 `FUSE_PCIE_GEN3_DIS` `0x00820580` 都读为 `0x00000001`；同时 `FUSE_PCIE_MAGIC_D` `0x00820520` 为 `0x16680000`。即使把 PHY 速率强制设为具备 Gen3 能力的 `0x00340036`，支持速度向量仍会被裁剪到 `0x00000006`。目前有两个问题未解决：残余上限是由同一组 DEVINIT 字节再次写入造成的，还是由下游独立强制执行熔丝三元组造成的；以及在拥有可重新签名的闪存时，仅修改这 5 个 DEVINIT 字节是否足以恢复 Gen4。参见[Gen3 和 Gen4](../frontier/pcie-gen3-gen4.md)。

### DEVINIT 与 ECC

> [!NOTE]
> **这里的证据指向 DEVINIT 之外**
>
> **这份 VBIOS 分析没有提供 DEVINIT 控制 ECC 的证据。** 整个 ROM 对比中唯一与 ECC 相关的事实是：InfoROM 的 `ECC` 对象存在于 A100，而不存在于 170HX。在 54.5 KB 的配置表区域中，没有任何位置发现 DEVINIT 侧的 ECC 字节。聊天中的一些理论将 170HX 的 ECC 行为归因于 DEVINIT，但静态分析并不支持这种说法。这是明显的证据缺失，而不是正面证据，因此置信度为中等。

从晶片侧也能得到佐证：`FEAT_OVR_ECC_PLM` `0x00823800` 冷读为 `0xffffff8f`，并控制 `0x82380c`、`0x823810` 和 `0x82382C`。HS ROP 可以打开它，但**打开后没有实际效果**，因为 `0x823814` 处的 ECC 使能回读由 POR/熔丝锁存，对运行时覆盖写入没有响应；而且这些覆盖值无论如何都会在 FLR 时恢复。名为 `ecc` 的分支完全不包含 ECC 代码（只有一条提交，"Fixed dual geometry support"）。ECC 已由熔丝关闭，目前没有已知的突破手段。至于 HBM 堆叠是否携带 ECC 配置，目前只能部分回答：A100 每个 FBPA 的 `CSTATUS_RAMAMOUNT` 差值被解读为同一批堆叠内部为 ECC 预留了容量，但这只是参与者个人的推断，并非数据手册结论。参见[ECC](../frontier/ecc.md)。

### 在运行时重新执行 DEVINIT

> [!WARNING]
> **实验性**
>
> 通过 PMU 在运行时重新执行 DEVINIT，**确实**在一张卡的一次会话中改变了硬件状态，但没有带来更多可用显存。

| 寄存器 | 之前 | 之后 |
|---|---|---|
| CFG1 `0x009a0204` | `0x02669000` | `0x22779000` |
| CSTATUS | `0x00000800` | `0x00000800`（不变） |
| LMR `0x00100ce0` | `0x0000028a` | `0x0000028a`（不变） |
| `0x9a038c` | `0xa7` | `0xa6` |
| `0x9a0330` | `0x00100093` | `0x0010009c` |
| `0x9a0334` | `0x002000cf` | `0x00200041` |
| `0x9a0338` | `0x003000ea` | `0x003000f1` |
| `0x9a0390` | `0x00c0052d` | `0x00c00528` |
| `0x9a0394` | `0x000028d9` | `0x0000394f` |
| `0x9a0300` | `0x00000003` | `0x00000003`（不变） |

七个 HBM 时序寄存器中有六个切换到了跳线 5 的值，但几何布局仍解析为 40960 MiB，因为档位 `0x77` 被减半为每个 FBPA 2048 MiB，覆盖 20 个活动 FBPA。跳线 5 的时序本身无法加载。频道内有人将这种结果状态非正式地称为 "the pg199 config"。PG199 是 NVIDIA 对 Drive A100 的板卡代码，也存在一个同名未发布分支；但 `0x22779000` 并不是任何发布版或分支代码写入的值，因此不应把这个标签理解为工具实现的某种配置。

还要注意，**发布版工具和所有未发布分支都不会重新执行 DEVINIT、驱动 PMU 或接触 FBFLCN。** 对完整分支集合搜索 `devinit`、`PMU`、`FBFLCN` 和 `0x101000` 都没有命中。这里描述的所有 DEVINIT 工作都存在于分析产物中，而不在发布版代码里。

### 显存时钟：同一时钟的四种倍数

VBIOS 中的显存时钟字段是**四分之一速率**。这解决了过去两年里把 432、729 和 1458 MHz 当成互相矛盾的三种记录这一问题。

| 关系 | 倍数 | `92.00.67`（364 MHz 字段） | `92.00.6D.00.0A`（432 MHz 字段） |
|---|---|---|---|
| VBIOS 字段 | ×1 | 364 MHz | 432 MHz |
| CUDA `deviceQuery` 显存时钟速率 | ×2 | 729 MHz | |
| 营销 / 规格 MHz | ×4 | 1458 MHz | 1728 MHz |
| Gbps 有效 | ×8 ÷ 1000 | 2.9 Gbps | |

1728 MHz 这一数值已通过一张运行 `0A` 映像的卡上的 `nvidia-smi` 确认。

> [!NOTE]
> **未解问题**
>
> `0A` 映像中的 `1728 MHz` 究竟是有效跳线值还是 boost 点。有人直接询问过，得到的回答明确只是猜测：“我想说是 boost。” 该 VBIOS 是否还改变电压、功耗或核心时钟，也曾被问过，但没有得到回答。

### 公开的 TechPowerUp 映像

目前公开存在四份 CMP 170HX 映像。**“16 GB”和“0 GB”的容量标签都是错误的，而且两者都不能解锁显存。** TPU 的“Memory Size”列无法对应到 `.rom` 文件中的任何字段，因此不可靠。

| TPU 条目 | 标签 | 实际 | 设备 / 子系统 |
|---|---|---|---|
| 257744 | 8 GB | 8 GB 量产映像 | `10DE 20C2` / `10DE 1585` |
| 239457 | "16 GB" | 与普通 8 GB VBIOS 逐位相同，除了 `flash_status_ledger`，它在每次刷写时都变（包括在工厂） | `10DE 20C2` / `10DE 1585` |
| 268495 | "0 GB" | 300 W `92.00.6D.00.0A` OC ROM | `10DE 20C2` / `10DE 1585` |
| 268984 | 10 GB | 10 GB 映像 | `10DE 2082` / `10DE 1557` |

TPU 268495 通过完整字段匹配被识别为 300 W ROM：版本 `92.00.6D.00.0A`、构建日期 2022-04-07、1020 KB、设备 `0x10DE 0x20C2`、子系统 `10DE 1585`、MD5 `a58aae86e72b13d50603c15653350664`、SHA1 `efad37d514bb94ac345719a0c56d9cd147cddfb7`、不支持 UEFI、GPU 时钟 1140 MHz、boost 1410 MHz、显存时钟 432 MHz、HBM2、报告显存大小为 0 MB、板卡功耗目标 250.0 W、上限 300.0 W、调整范围 -60% / +20%。

一位将 239457 刷到 268495 上的测试者报告，显存频率降低了约 300 MHz，功耗上限降至 250 W，也不再有可用的核心偏移。这与从 300 W 映像的 432 MHz 字段切换到 250 W 映像的 364 MHz 字段相符，有效频率下降 272 MHz。

> [!CAUTION]
> **TPU 条目 283106 不是 CMP 170HX，绝不能刷入 CMP 170HX**
>
> 283106 是一份 NVIDIA A100 / DRIVE-PG199-PROD 映像：版本 `92.00.A0.00.01`、构建日期 2022-07-08、976 KB、MD5 `ba22571080e412612964d130f0ce3880`、SHA1 `ccac3c86cb901c5bb6758d3423d00383e6355c13`、设备 `0x10DE 0x20BB`、子系统 `10DE 14A1`、显存大小 32751 MB、GPU 时钟 1260 MHz、boost 1260 MHz、显存时钟 351 MHz、HBM2，且没有板卡功耗上限块。它曾以“170HX 参考映像”的名义流传。通过 SPI 编程器刷入后，`dmesg` 出现 `NVRM: GPU 0000:0d:00.0: RmInitAdapter failed! (0x62:0x55:2674)`，报告的 DevID 仍为 `10DE:20C2`。之后有人在 Windows 笔记本上使用 `omgvflash` 再次尝试，导致蓝屏。

> [!NOTE]
> **未解问题**
>
> 是否存在一份真正不同的“16 GB”170HX ROM。对比合集将 `cmp170hx_16gb_92.00.67.00.01.rom` 列为独立文件，但它的版本、构建日期、设备 ID 和子系统都与 8 GB 映像相同，并标注“no cards ever shipped”（从未有卡出厂使用）；另外，TPU 239457 已被发现与 8 GB VBIOS 逐位相同。它们可能只是同一文件被重复计数。将合集文件与 239457、257744 的 MD5 或 SHA 进行比对即可定论。

### SKU 内部及跨产品 ROM 差异

| 对比 | 总差异 | 分解 |
|---|---|---|
| 170HX 8 GB vs 10 GB | 2,684 B | NVGI `0x0000`-`0x5E00` 2,399 B（包括四个约 384 B 的 MAC 块、约 1,533 B MAC 内容）；PciAt `0x5E00`-`0xC000` 36 B，全是版本和设备 ID；FwSec 主体 `0xC700`-`0x47700` 249 B，仅训练和配置 |
| Drive A100 vs A100 PCIe 40 GB | 468,557 B（ROM 的 45%） | 签名范围大 96 KB 加一个完全不同的固件构建 |
| Drive A100 GPU0 vs GPU1 | 49,852 B | 49,797 B（99.5%）InfoROM、55 B NVGI：相同固件，仅按单元校准 |

8 GB 和 10 GB 映像的 NVGI 引导程序中**只有两个字节不同**：`0x0004` 为 `0x52` 或 `0x80`（头大小/版本字段），`0x000E` 为 `0x85` 或 `0x57`，编码子系统 ID 的低字节 `0x1585` 或 `0x1557`。扣除 MAC 内容后，真正具有功能意义的 SKU 差异非常小，这与七字节限制的数量相符。

已发布的 Drive A100 区域分解（NVGI 155 B、PciAt 4,799 B、FwSec 主体 91,694 B、未签名尾部 11,142 B、InfoROM 52,847 B）总和为 160,637 B，而不是 468,557 B。这是源分析中的真实矛盾。最可能的解释是，区域表只覆盖重叠窗口，而总差异是对两份映像进行整文件比较得到的；两份映像的签名范围相差 96 KB，导致其后的所有区域发生偏移。目前没有任何来源能够调和这一矛盾。

**每条 GA100 产品线的 FwSec 主体大小都不同。** 因此，从结构上就可以排除 FwSec/VN 映像交换，而不只是因为尚未测试：

| 映像 | FwSec 主体 | 跨度 |
|---|---|---|
| 170HX 8 GB / 10 GB / "16 GB" | 241,664 B（基线） | `0xC700`-`0x47700` |
| 170HX 300 W | 242,176 B（+512） | `0xC700`-`0x47900` |
| A100 SXM4 40 GB | 240,640 B（-1024） | `0xC700`-`0x47300` |
| A100 PCIe 40 GB | 244,224 B（+2560） | `0xC700`-`0x48100` |
| Drive A100 32 GB | **未解决**：记录的正文大小（362,496 B）与记录的跨度不符；`0x5AC00 - 0xC700` = 320,768 B。在重读定论前用跨度而非总数 | `0xC700`-`0x5AC00` |

170HX 各 SKU 的 VN 前导相同，这是唯一一处会让交换看起来可行的地方。

## 哪些可以修改，哪些不可以

以下五个目标按是否属于 MAC 范围排序。

| 目标 | 偏移量 | 在 MAC 内？ | 状态 |
|---|---|---|---|
| CFG1 跳线 4 档位字节 | `0x41D53` | 内 | **不可行。** 需要 csecret(2)。2026-05-08 在此翻转一个字节后 Booter 卡死，证明了这一点 |
| PCIe Gen1 锁，5 字节 / 3 个 DEVINIT 位置 | 位于 `0x33800`-`0x41200` | 内 | **不可行。** 已由运行时 Gen2 分支取代 |
| ECB 固件块 | `0x14A00`-`0x33800` | 内，且用 csecret(6) 加密 | 内容未知 |
| 功耗上限从 250 W 到 300 W | `0x45E45` | 外 | **开放但未测试。** 只能使用 CH341A |
| `CTRL_OPT` 熔丝表 | `0x47341` | 外 | 调查中，语义未确定 |

### 写入路径：先验证再写会将载荷绑定到映像

一次受控的 2×2 实验（通过 VV 认证的映像 × EWR 载荷）确立了以下规则：

| VV'd 映像 | EWR 载荷 | 结果 |
|---|---|---|
| live | live | ERR = 0 |
| live | 8 GB | `0x9C` |
| 8 GB | 8 GB | ERR = 0（成功） |
| 8 GB | live | `0x9C` |

第四行最关键：载荷明明是当前闪存中的实际内容，仍然会被拒绝，因为 VV 认证的是另一份映像。规则是：先用 VV 认证一份确实带签名的映像，再写入*那份映像的*字节。研究者将 7,878 字节的外来 8 GB 内容写入真实 VBIOS 块，读回后再逐字节恢复，从端到端验证了这一规则。**因此，一份确实带签名的 80 GB A100 VBIOS 可以刷入；修改过的映像则会更早在 VV 的 `0x40` 处失败。**

> [!NOTE]
> **未解问题**
>
> 目前缺少的是一份能在启动时通过 170HX 板卡 ID 和熔断设备 ID 检查的签名映像。到目前为止，每次跨刷都失败在这道启动检查上，而不是失败在写入阶段。最直接的下一步，是对一张 250 W 卡执行一次**同 SKU** 300 W ROM 的 VV+EWR；该 ROM 有签名、设备 ID 相同且板卡相同，可以用来确定启动侧检查依据的是板卡 ID，还是更严格的条件。

## 失败特征

任何刷写尝试前都应把这张表放在手边。另见[排障](../procedures/troubleshooting.md)。

| 签名 | 含义 |
|---|---|
| `GFW_BOOT = 0x401` 或 `0x001` | MAC 损坏。签名范围内的某个字节发生了变化 |
| `GFW_BOOT = 0x8F`，PROM 读全 `0xFF` | FWSEC HS 退出污染。FWSEC 已运行，但 GFW 从未通过这一步，因此驱动永远到不了 Booter |
| `kgspExtractVbiosFromRom_TU102: did not find valid ROM signature` 然后 `RmInitAdapter failed! (0x62:0x25:2028)` | VBIOS 状态寄存器（SReg）数据已损坏。**重新刷入出厂 ROM 也无法恢复** |
| `kgspWaitForGfwBootOk_TU102: failed to wait for GFW boot complete: 0x65` | 在 `92.00.66.00.02` 上尝试修改 VBIOS 时出现 |
| `RmInitAdapter failed! (0x62:0x55:2674)`，DevID 不变 | 刷入了外来的（Drive A100）映像，但没有产生任何功能变化 |
| `nvflash` 的 `falcon halted` | `nvflash` 通过 `--protectoff` 绕过了映像验证，但在运行自己的 SPI 写入器 ucode 时失败 |
| VV 错误 `0x40` | 修改过的映像在写入阶段之前的验证阶段被拒绝 |
| `0xBADF3000` | 上电前 SPI 未写保护 |
| Device Manager Code 10（Windows） | 测试者生产的每一份本地修补的 170HX VBIOS 都给出这个 |

## 失败路线

每一项都是真实尝试及其真实结果。除非获得新信息，否则不应重复尝试。完整的项目级清单见[失败路线](../history/dead-ends.md)。

| 尝试 | 结果 |
|---|---|
| 将完整 A100 VBIOS 跨刷到 170HX | 显卡在安全模式下无法启动，因而不可用；显存大小、SM 数量和着色器数量都没有变化，只有子系统 ID 改变。2024-07-17 证伪，2026-07-19 和 2026-07-25 再次确认 |
| 将 A100 VBIOS 刷到一张修改过跳线的 10 GB 卡 | 显卡变砖。恢复时必须使用 SPI 编程器刷回保存的原始 ROM |
| 将映像中的跳线字节从 `44` 改为 `66` 并修复校验和 | 驱动加载失败。这与 Falcon 在上电时验证映像并将晶片置于非安全模式的情况一致。后来改用 `0x009a0204` 处的运行时 CFG1 写入 |
| 在签名范围内翻转单个字节（`0x41D53`） | Booter 卡死，`GFW_BOOT=0x001` |
| 简单拼接 ROM，将 A100 区段接入 170HX 映像 | 两方面都会失败：各 ROM 的跳线表偏移不同，而且每个区段都有独立的 MAC |
| 在不同 SKU 之间交换 FwSec / VN 映像 | 由于主体大小不匹配，从结构上排除 |
| 移植 A30 FWSEC 模块 | 一开始就失败：10 GB 170HX 与 A30 的签名代码模块已经**相同**，所以移植模块没有任何收益。真正不同的是已验证区内的非代码配置 |
| 使用打过补丁的映像验证和 `--protectoff` 的 `nvflash` | 能走得更远，但在 nvflash 运行其 ucode（也就是 SPI 写入器本身）时出现 `falcon halted`。`omgvflash` 和 `nvflashk` 同样拒绝修改过的 BIOS |
| 从软件写入 SPI 控制器寄存器 | 见下文。已彻底排除 |
| 将 NVGI 作为攻击面 | 被启动顺序排除：DEVINIT 会覆盖 NVGI 对 MR1/MR2/MR3 的写入，而 FWSEC 会重新提高 NVGI 降低的任何 PLM |
| 对 VBIOS 发起 TOCTOU | 结果是 SReg 数据被擦除；显卡因没有有效 ROM 签名而失败，重新刷入出厂 ROM 也无法恢复 |
| 将 8 GB VBIOS 刷到 10 GB 卡 | 使用打过补丁的 nvflash 成功刷入并恢复，但 8 GB 映像无法在 10 GB 卡上启动，跳线修改也未通过刷写时的映像检查。注意：两次刷写之间没有重启，因此这个结果只能作为提示，不能下定论 |
| 将 Maxwell 时代的 ECC 解锁移植到 Ampere | 从未在 GA100 上演示；其作者本人也提醒说，在 Ampere 上并不简单 |
| 以仿真/模拟 HBM2e ROM 为模板 | 模拟 ROM 约 230 KB，布局完全不同；即使在其中，只有主跳线表从 `66` 提升到 `77`，而 `0x1AD72` 处的副本仍然是 `00 90 66 02` |
| 修改已经解密的 VBIOS | 已找到欠压和显存时序位置，但**每次修改都会导致驱动加载失败**。从未尝试给驱动打补丁，使其接受修改后的状态 |
| 为定制 VBIOS 自行签名 | 据报告，在泄露窗口期间曾短暂可行。现在没有可用的签名能力。泄露窗口的细节应视为轶闻 |
| 把 VBIOS 修改作为绕过 GSP-RM 问题的路径 | 返回“Checksum failed”。通过刷写 VBIOS 绕过 Booter 的晶片 ID 检查“完全不起作用” |
| 相信 TechPowerUp 的“Memory Size”列 | 它无法对应 `.rom` 文件中的任何字段 |

### SPI 控制器无法由软件写入

这里明确记录结论，以免重复尝试。refire-chain HS 利用**确实**成功打开了 `0xD7D8` 处的 SPI PLM，将其设为 `0x00000000`，并通过 rp=0、wp=0 确认已打开。这证明该利用可以从 HS 模式访问并修改 PLM。尽管 PLM 回读显示完全开放：

| 寄存器 | 写入 | 回读 |
|---|---|---|
| `SPI_DATA` `0xE4A0` | 从 PL0 `0xDEADBEEF` | `0x00000000` |
| `SPI_CTRL` `0xE5A0` | 从 PL0 `0xDEADBEEF` | `0x00000000` |
| `ROM_SERIAL_BYPASS` `0xE204` | 从 PL0 `0xDEADBEEF` | `0x00000000` |
| `0xE4A0` / `0xE5A0` | 直接 HS-ROP 写入 | 报告 "~"（未落地），寄存器停在 `0x0` |

结论是：安全启动状态机强制执行一个硬件写入过滤器，除 GFW 引导固件（启动期间的 SEC2/PMU）外，其他代理对 SPI 控制器的所有写入都会被丢弃。**在这张卡上，不存在任何软件路径可以写入 CFG1 对应的闪存字节。**

## 特定于 VBIOS 的开放问题

以下按最容易处理的项目优先排列。跨领域问题清单见[未解问题](../frontier/open-questions.md)。

1. **将 `0x45E45` 处的功耗上限从 250 W 刷到 300 W。** 三字节字段当前为 `90 D0 03`，应改为 `E0 93 04`。它位于 15,616 字节未签名尾部（`0x43A00`-`0x47700`）起始后 9,285 字节处，因此不会破坏 MAC，与已经成功启动的 `0xFF` 填充测试属于同类修改。目前唯一的阻碍是“即使修改未签名尾部，`nvflash` 也会拒绝”，所以需要 CH341A、拆下散热器并重新涂导热膏。该项目自 2026-05-09 起开放，但尚未测试。
2. **确定 `NV_FUSE_CTRL_OPT_*` 的语义。** `0x47341` 处的 25 项表，在探测过的 13 张 GA100 卡上都读为全零。另一个相关点是：`0x001404` 处的 `PBUS_SW_SCRATCH(1)` 读为 `0x20042000`，位 14 已清除；有人认为（但从未进行写入测试）该位会让固件跳过 CTRL_OPT 清零循环。对于熔丝已经处于下限的卡，这个机制没有实际效果。
3. **在 `0xFE504` 注入 HULK 证书**（见上文）。
4. **恢复 csecret(2)。** 这将一次性开放 MAC 范围内的所有修改，也就是全部七个限制字节。离线预言机使 DFA 行动不再需要反复刷写。工作量极高。
5. **确认未签名尾部的显存修改是否生效。** 即上文描述的 `freqDelta` 实验。
6. **通过调试 IMEM 方法解密量产 Falcon/DEVINIT 代码。**
7. **A30 对齐线索。** 据报告，一份 A30 VBIOS `92.00.66.00.0x` 与 10 GB 170HX 的 `92.00.66.00.0x` 几乎相同，理由是 A30 是一颗启用了三个 HBM2 堆叠的 A100，而堆叠数量由熔丝控制。问题在于签名代码模块已经相同，因此唯一有价值的是覆盖范围内的非代码配置数据，而这正是需要 csecret(2) 的部分。将 A30 ROM 与 10 GB 170HX ROM 做差异比较，可以列出这些配置差异。
8. **比较软件与硬件 SPI 流量。** 未经验证的三手说法称，`nvflash`/`omgvflash` 会写入裸 SPI 编程器不会触及的“中间寄存器”。在软件刷写和硬件刷写期间监视 SPI 总线，使用逻辑分析仪即可低成本地验证这一说法。

> [!NOTE]
> **未解问题**
>
> 跳线表*在实际启动中是否经过 MAC 验证*。一种观点认为，即使 `0x41D53` 位于声明范围内，Falcon 也可能实际不检查它。相反的证据是 2026-05-08 在这一精确偏移处进行的字节翻转测试：测试使 Booter 卡死。目前证据明显倾向于“它确实会被验证”。复杂之处在于，*观察到的*频道内失败（“不能修改跳线，否则映像检查失败”）是**主机侧 nvflash 检查**，而不是启动时 Falcon 的检查，因此双方讨论的并不完全是同一个问题。使用 CH341A 刷入一份修改过跳线的映像，完全绕过 nvflash，再读取一次 `GFW_BOOT`，即可定论。目前没有人报告做过这项测试。

> [!NOTE]
> **未解问题**
>
> 170HX 的限制究竟驻留在熔丝中还是 VBIOS 中。工程样品 A/B 刷写表明，VBIOS 携带显存上限、PCIe 上限以及*部分*算力惩罚，但并非全部：将一份 170HX VBIOS 跨刷到一颗会跳过签名检查的工程样品 GA100 上，只施加了 **1/12 FP64 和 1/8 FP32** 的限制；真实 170HX 上则是 **1/64 和 1/32**。这意味着 FP64 约有 5 倍、FP32 约有 4 倍的残余因子，必然来自其他位置。发布版解锁通过运行时写入 SS0/SS1 恢复完整 SM 吞吐，强烈暗示剩余部分来自由 `0x00823804` 控制的特性覆盖；但工程样品实验从未在同时写入 SS0/SS1 的条件下重做。发布版解锁是纯软件实现，并不能解决这个问题：它只是运行时覆盖状态，不能证明默认值的来源。

> [!NOTE]
> **未解问题**
>
> 供应商是否存在批次级 VBIOS 差异。一位自称某批量持有方技术员工、且具有商业利益关系的消息来源说：“we have two kinds of VBIOS for 170hx here, one has higher bandwidth”（我们这里有两种 170hx 的 VBIOS，其中一种带宽更高）。对方没有提供版本字符串或带宽数值。这一说法至少与 `92.00.67.00.01`（364 MHz 字段）和 `92.00.6D.00.0A`（432 MHz 字段）都在实际流通这一事实相符。现有记录无法解决这个问题。
