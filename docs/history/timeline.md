# 项目时间线

## 本页覆盖内容

这是一份有日期标记的记录，讲述 CMP 170HX 如何从一张受熔丝限制的矿卡，变成一张拥有 64 GB 显存、以全速运行的 GA100。时间线覆盖活跃期 **2026-06-22 到 2026-07-28**，并补充了促成这一切的早期背景。聊天时间戳默认使用 UTC，除非明确给出本地偏移；精确到秒的时间，要么是从消息 snowflake 解码得到的，要么是从 git 作者时间戳读取的。Git 表格中的日期按**作者的本地偏移**（大多为 `-07:00`）记录，这也是提交自身呈现日期的方式；因此这里有三个分支 tip 比其 UTC 时间早一个日历日。

读者应重点记住以下五个里程碑：

| 日期 | 里程碑 |
|---|---|
| **2026-07-12** | 算力解锁在硬件上成功运行。一个手动执行的五步 TTY 流程解除 1/32 的 FP32 节流；实测 SGEMM 为 12.28 TFLOPS |
| **2026-07-14 / 15** | `cmpunlocker` 公开发布。首个版本是一个**免驱动 Python** 算力解锁器，完全不修改驱动 |
| **2026-07-18** | 显存几何布局发布。8 GB 卡解锁到 **64 GB**，10 GB 卡解锁到 **40 GB**，而且驱动内方案在一天之内完成 |
| **2026-07-23 / 24** | 免驱动方案以独立 Python refire 链的形式回归，同时宣布支持 **PCIe Gen2** |
| **2026-07-26 / 27** | Gen2 分支谱系趋于稳定；在一张经过电容改装的卡上捕获到一次 Gen2 x16 观察结果 |

按照贯穿整个维基的规则，本时间线严格区分两件事：PCIe 链路**速度**（从 Gen1 提升到 Gen2，这是软件和固件层面的解锁）与 PCIe 链路**位宽**（从 x4 提升到 x16，只能通过手工焊接 24 颗原本缺失的电容实现）。它们是不同日期取得的不同成果。参见[PCIe 子系统](../hardware/pcie-subsystem.md)和[物理改装](../operations/physical-mods.md)。

## 2026-07-12 到 2026-07-17：算力落地，仓库公开

### 算力解锁

**2026-07-12** 是解除算力节流的日期。在任何驱动内补丁出现之前，能够工作的手动流程是：

```text
run the ROP script  ->  FLR  ->  kill the NVIDIA driver  ->  FLR again  ->  run the SM unlock script
```

FLR 指的是 `echo 1 | sudo tee /sys/bus/pci/devices/0000:${PCI}/reset`。这条命令必须从 TTY 执行。使用的驱动是版本 580.159.04 的开源内核模块，`patch_gsp.py` 会将载荷拼接进 `gsp_tu10x.bin`。`Guide_SM.sh` 将流程实现为一个三次写入的 ROP 阶段（CFG1 `0x02779000`、LMR `0x0000020B`、PLM `0xFFFFFFFF`），然后执行一次 FLR、强制卸载驱动、第二次 FLR，最后通过 `resource0` 写入 `0x0082381C = 0x88888888` 和 `0x00823820 = 0x00000008`，并进行读回验证。

同日测得：首次完成完整 SM 解锁后，SGEMM FP32 达到 **12.28 TFLOPS**，由两名独立测试者报告。那次会话没有在同一张卡上测量锁定状态的基线。同期公布的“32 倍”是由熔丝值 `0x5` 所隐含的架构除数；引用的约 0.38 TFLOPS 出厂速率是用 12.28 除以 32 得出的，并非单独测量结果。另有一次独立测量得到约 0.39 TFLOPS 的锁定速率，为这个除数提供了佐证；参见[性能](../operations/performance.md)。出厂 `FEATURE_OVERRIDE` 区块被完整转储（`regs_01.txt`），并确认主灭杀熔丝 `0x008203f0` 未烧断，读数为 `0x00000000`，这正是上述解锁成为可能的原因。

为达到这个结果，前后执行了**超过 1100 次 fire**，其中真正不同的尝试只有约 50 次。完成这项工作的人后来这样说：“I just couldn't have known that in advance.”（“我事先根本不可能知道这一点。”）

| 10 GB | `10de:2082` | 10240 MiB | **40960 MiB (40 GB)** | `0x02669000` | `0x0000028A` | `0x0000000A00000000` |

两种 SKU 的出厂 CFG1 都是 `0x02449000`；出厂 LMR 则分别是 `0x00000208`（8 GB 卡）和 `0x00000288`（10 GB 卡）。同样在 2026-07-18，`multiple-cards` 分支完成提交，`housekeeping` 分支为所有补丁加入 `0x2082` 支持，master 提交 `0f9aca5 "Unlock isn't gated anymore"` 则把安装门槛从仅允许 `0x20C2` 扩大为同时允许 `0x20C2` 和 `0x2082`。

完整细节见[显存几何布局](../unlock/memory-geometry.md)和[六个驱动补丁](../unlock/driver-patches.md)。

## 里程碑总结

| 成就 | 日期 | 持久性 | 已在 `master` 发布？ |
|---|---|---|---|
| FP32 FMA 编译时变通方案（约 16 倍，6.25 TFLOPS） | 2023-10-27 | 源码级，按应用生效 | 不是驱动功能 |
| 移除算力节流（SS0/SS1，全速） | 2026-07-12 | 可挺过 FLR（常电域） | **是** |
| `cmpunlocker` 公开，免驱动 Python | 2026-07-14 / 15 | 每次引导重新应用 | 2026-07-18 被移除 |
| 显存几何布局，8 GB 到 64 GB、10 GB 到 40 GB | 2026-07-18 | **无法**挺过 FLR 或断电重启 | **是** |
| 多卡支持 | 2026-07-18 / 19 | 每次引导重新应用 | 否，仅存在于分支 |
| 10 GB 卡上的 80 GB | 2026-07-19 | 已尝试，超过约 40 GB 后不稳定 | 否，而且不应发布 |
| 免驱动 SEC2 refire 链（v1 到 v6） | 2026-07-22 到 24 | 每次引导重新应用，GPU 必须解绑 | 否，平行方案 |
| PCIe Gen2（速度，x4） | 2026-07-24 | 每次引导重新应用，分支中为驱动内方案 | 否，仅存在于分支 |
| PCIe x16（位宽，通过焊接实现） | 硬件改装，日期不限 | 永久，物理层面 | 不是软件功能 |
| Gen2 x16 组合 | 2026-07-26，一次观察 | 尚未确立 | 否 |

> [!CAUTION]
> **80 GB 档位不是一个里程碑**
>
> `80` 分支报告的容量约为 81920 MiB，即 85,545,582,592 字节，并且 `cudaMalloc` 分配 77 GiB 成功；但在 80 GB 配置下，访问超过约 40 GB 的 kernel 会导致 GPU 致命丢失，与功耗上限无关。报告的 Xid 代码包括 Xid 31（被描述为无害）以及 CUDA 显存测试后的 Xid 154；最常见的症状是卡死。单独出现 Xid 31 是一名旁观者提出的说法，持有故障卡的操作者并未确认它就是**该故障的特征**。除非将上限设为 39 GB，否则 `cuda_memtest` 会卡死。因此最终发布的是 40 GB，而不是 80 GB。参见[80 GB 问题](../frontier/80gb.md)。
